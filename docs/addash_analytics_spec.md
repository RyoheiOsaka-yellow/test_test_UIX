# addash 分析ロジック仕様書

> **役割分担**: 別チャンネルでUI/UX（デザイン）を、本仕様書でロジック・分析項目を定義する。
> UIの器は先行実装されており、本仕様は「どの器に・何を計算して流し込むか」を定める。
>
> **製品の核となる要件**:
> 1. 高度な分析ロジック（メタ/Google/TikTok等の横断統合）
> 2. 美しいレポート出力
> 3. データを毎日触りたくなるUX
> 4. 業種・業態ごとのDB選択
> 5. 将来：人流分析・ビーコンの統合
>
> **配信前提**: 単一HTMLファイル / ブラウザ完結 / Anthropic API はブラウザではCORSで失敗するため scripted/mock 応答、実APIはサーバーサイド実装に限定。

## エグゼクティブサマリー（開発着手用）

### この仕様の全体像

広告配信ダッシュボードの分析ロジックを、深さ別の5層（L0記述→L1診断→L2予測→L3処方→L4生成）＋6つの横断軸（A:オフライン統合[LM社協業]／A-2:オフライン各層適用／B:媒体プロファイル／C:追加6観点／D:販促CP統合／E:統一表現レイヤー）で定義する。xADの入口は**ボード選択エンジン**（広告タイプ×業種×データ充足の3軸で最適ボードを構成）。広告タイプは処理系統も分岐させ、**販促ボードは広告効果推計エンジン**（Google Meridian＋GeoLift＋人流注入のマルチシグナル統合）で動く。出し分けは業種×レイヤー適用マトリクス（実装詳細5）がSSOT。UIの器は別チャンネルで先行実装済みのため、本仕様は「どの器に何を計算して流し込むか」を定める。

> **新規性の定義**: 「AI×広告×増分の統合計測（UMM）」は世界の業界標準だが、人流・EO・決済等のフィジカルセンシングを同エンジンに統合した例は世界未踏。日本の販促文脈×LM社人流は国内空白。xADは「広告計測×フィジカルセンシングの架橋」が新規性。土台はオープンソース（Meridian/GeoLift）に乗り、独自部分（人流統合）に集中。

### 貫く設計原則（全層共通）

1. **少データで動く→賢くなる**: どの分析も初期は軽量な近似で必ず何か返し、データ蓄積で高度化する。ゼロから完璧を待たない。
2. **ロジックが判断、LLMは翻訳**: 数値判断・提案選定・優先度は全てロジック。LLMは確定した構造化データの言語化のみ（幻覚・再現性・CORS制約への対応）。`window.__scriptedReply`フォールバック必須。
3. **精度を正直に開示**: 推定値・補正値・相関（≠因果）は、その確からしさを常にUIに明示する。これが「分析精度を誇る製品」の信頼の源泉。
4. **媒体・業種は設定で吸収**: ロジック本体は媒体名も業種名も知らない。媒体プロファイル／業種パラメータセットの追加だけで拡張できる。
5. **毎日触りたくなる = 変化の検知（L1）＋示唆の更新（L3）。裏返せば毎日うんざりさせない（⑥アラート制御）。**
6. **デモと本番でアーキテクチャ分離**: デモ＝ボード単位の単一HTML（軽量・scripted・営業/検証用）、本番＝Vite+React+TS＋サーバー（実API・LM社連携・重い計算）。重い数値計算（ASCM/DML/プラセボ検定）はサーバー、ブラウザは軽い計算と表示。デモと本番はインターフェースを揃えデータソースだけ差し替える（`window.__scriptedReply`パターン）。

## ボード選択エンジン（xADの入口）

xADは「クライアントの状況を見て最適なボードを構成して出す」プラットフォーム。本エンジンがその入口。実装詳細5の適用マトリクス（業種×レイヤー）を内包し、その上位に「広告タイプ」「データ充足」を足した3軸で最適ボードを決める。

### 最適ボードを決める3軸

| 軸 | 値の例 | 何を決めるか |
|---|---|---|
| **広告タイプ** | メタのみ / 横断（複数媒体）/ 販促（人流込み） | どのレイヤーを点灯するか（大枠） |
| **業種** | EC / 薬局 / 葬儀 / ウェディング… | KPI定義・閾値・訴求軸辞書（パラメータ） |
| **データ充足** | 接続済み媒体・人流有無・POS有無・CRM有無 | 実際に動かせる範囲 |

最適ボード = 3軸の交差点。広告タイプがレイヤーの大枠、業種がパラメータ、データ充足が実出力範囲を絞る。実装詳細5は2軸目（業種×レイヤー）に相当し、本エンジンが広告タイプとデータ充足を上位に足して完全化する。

### 動作フロー

```
1. クライアント登録 → 広告タイプを判定/選択（メタのみ/横断/販促）
2. 広告タイプ → 候補レイヤーセット決定（販促なら人流レイヤーをON候補に）
3. 業種 → パラメータセットをロード（KPI定義・訴求軸辞書・閾値）
4. データ接続状況 → 実際に点灯できるレイヤーを確定（人流未接続なら人流ボードはグレーアウト）
5. 確定したボード構成を出力 → クライアントスイッチャーで切替
```
ステップ2-4は実装詳細5のフラグ（useFootTraffic等）とデータ充足バッジ（判断C）を再利用。新規に足すのは最上位の「広告タイプ」軸のみ。

### 決定事項

1. 最適ボード = 広告タイプ×業種×データ充足の3軸の交差点。実装詳細5を内包し、広告タイプとデータ充足を上位に足す。
2. 動作フロー：広告タイプ判定→候補レイヤー→業種パラメータ→データ充足で確定→ボード構成出力。
3. 広告タイプは自動推定＋手動上書き（接続データから初期推定。人流接続済→販促、メタのみ→メタタイプ）。
4. 広告タイプがプリセット構成を決め、運用者が要素単位で調整可能（プリセット＋上級者調整）。実物のクライアント/テーマスイッチャーの粒度で要素ON/OFF。
5. 広告タイプも事業ライン単位（論点Dと接続）。**事業ライン = 広告タイプ×業種×データ充足の1セット**と定義。
6. 未接続データはグレーアウト＋接続導線（隠さず「LM社データを接続すると有効化」と促す。アップセル導線）。

## 分析ロジックの5層モデル（全体地図）

分析の「深さ」で5層に整理する（L0〜L3＋生成のL4）。下層ほど高度で差別化が効く。依存関係により、攻める順序は L0 → L3配分最適化 → L1 → L3アクション生成 → L2 → オフライン統合。L4生成はL1-L3の蓄積を入力に動く。

| 層 | 問い | 主な項目 |
|---|---|---|
| **L0 記述層** | What happened | KPI集計、**媒体横断の統一CV定義**、時系列集計 |
| **L1 診断層** | Why | 異常検知、寄与度分解、統計的有意差、クリエイティブ疲弊検知 |
| **L2 予測層** | What will happen | 着地予測、レスポンスカーブ推定 |
| **L3 処方層** | What to do | 予算配分最適化、AIアクション生成、クリエイティブ修正提案、競合/ベンチマーク示唆 |
| **L4 生成層** | Make it | クリエイティブ自動生成（プロンプト/テンプレート/A/B派生）、勝ちそう度予測、生成→効果→学習ループ |

> L4はxADのもう一本の柱（分析ボード選択＋クリエイティブ生成）。L1-L3の診断・予測・勝ち要素抽出を入力に、実データ駆動で生成する。L3-3クリエイティブ修正提案の上位・独立機能。

**横断軸（5系統。詳細は各セクション）**:
- **A: オフライン統合（LM社協業）** — 人流×広告のO2O二重接続。AREA MAP / BEACON LOG / O2O FUNNEL の器。L3の最終形。
- **A-2: オフライン各層適用** — L0〜L3を人流データに適用したオフライン版。
- **B: 媒体プロファイル** — 媒体差を1箇所に閉じ込め、設定追加で新媒体を足す。
- **C: 追加6観点** — データ品質／セグメント／LTV／ペーシング／学習ループ／アラート制御。
- **D: 販促CP統合** — オープン/クローズド/CRM連携CP。O2Oの下位接続。
- **業種別DB**: 同じL0〜L3でも業種でKPI定義・閾値・適用レイヤーが変わる（葬儀=資料請求、EC=購入、薬局=O2O来店）。業種パラメータセット＋適用マトリクス（実装詳細5）で制御。

**「毎日触りたくなるUX」の2本柱**:
- 変化の検知（昨日と違うことが起きた→見たくなる）= L1異常検知
- 示唆の更新（今日の打ち手が毎日変わる→従いたくなる）= L3アクション再生成

## 広告効果推計エンジン（販促ボードの裏側・マルチシグナル統合）

### 位置づけと処理系統の分岐

xADは広告タイプで**裏側の処理系統そのもの**を切り替える（ボード選択エンジンの拡張）。

| ボードタイプ | 処理系統 | 入力シグナル |
|---|---|---|
| メタのみ / オンライン横断 | 既存L0-L4（媒体データ中心） | 広告配信データのみ |
| **販促ボード** | **本推計エンジン**（マルチシグナル統合） | 広告＋人流＋EO＋ビーコン＋Wi-Fi＋決済＋販促CP |

メタのみボードにマルチシグナル推計は不要（シグナルが広告データだけなので動かす意味がない）。販促ボードは取れるシグナルを全部吸い込んで推計精度を上げる。**広告タイプがUIレイヤー・配分粒度・推計エンジンの3つを決める**。

### コンセプト：AI × 運用型広告 × 人流の掛け合わせ推計

広告配信を軸に、人流・EO・ビーコン・Wi-Fi・決済・販促CPなど取れるシグナルを片端から統合し「この広告がどれだけの成果を生んだか」を多元的に推計する基盤。AIが裏でこの統合・推計を回し続け、ボードはその出力を見せる窓。**シグナルが増えるほど推計精度が上がる**。

### 新規性の正確な定義（世界の現在地との対比）

- **既存（新しくない）**: 「AI×広告×増分の統合計測（UMM=Unified Marketing Measurement）」は2025-26年の業界標準。MMM＋増分テスト＋帰属をAIが統合し較正する方向は各社（Triple Whale, Measured, LiftLab, Dema等）が商用化済み。
- **未踏（新しい）**: それらが統合するのは広告データ系の手法のみ。**人流・EO・決済等のフィジカルセンシングシグナルを同じ推計エンジンに統合した例は世界でも見当たらない**。
- **国内空白**: 日本の販促文脈（オープン/クローズド/CRM CP）×LM社高精度GPS人流は完全な空白地帯。
- **結論**: 発想は世界の最前線にあるが、人流統合は世界でも未踏、それを国内販促文脈で実装するのがxADの新規性。「未統合だった2つの世界（広告計測×フィジカルセンシング）を繋ぐ」ことが価値。

### 技術土台：Google Meridian ＋ GeoLift ＋ 人流注入

車輪の再発明を避け、確立したオープンソースを土台に独自部分（人流統合）に集中する。

- **MMM土台 = Google Meridian**: 採用理由は(1)地域階層モデルがネイティブ（50+地域を階層構造で同時モデル化、穴#3の媒体×エリア粒度を既製で解決）、(2)ジオテスト較正がベイズMCMCで組み込み済み（論点Bの較正が標準機能）、(3)ベイズで信頼区間が出る（シグナル信頼度加重＋精度開示に必須）、(4)因果フレームワーク（予算を動かしたらどうなるかに答えられる＝L3-1直結）。RobynはMeta中心・地域分離が弱くリッジ回帰で信頼区間が出にくいため、人流という地域シグナル統合には不適。
- **ジオリフト = GeoLift**（採用済み）。MeridianのジオテストCalibrationと連携。
- **独自部分 = 人流をMeridianの地域シグナルとして注入**。Meridianは「地域ごとの売上を地域ごとのメディア投下で説明」するモデル。そこに人流を地域ごとの追加説明変数（コントロール変数/媒体効果の地域補正）として入れる。**MeridianユーザーはメディアデータしかMeridianに入れていない＝人流統合は世界未踏**。
- 自前レスポンスカーブ（べき乗→Hill）はMeridianのadstock＋飽和カーブに準拠/置換。

### シグナル抽象化層（何でも後から足せる構造）

すべての入力を統一インターフェースで受ける。各シグナルは中身と別に6属性のメタデータを持つ。

| メタ属性 | 意味 |
|---|---|
| 測定対象 | 何を測っているか（人流=店舗前通行、EO=駐車場車数） |
| 精度 | 真値からのブレ |
| 粒度 | 時間・空間の細かさ |
| カバレッジ | 母集団のどれだけを捉えるか |
| 鮮度 | 最新性 |
| 測定する量 | 量／質／単価のどれか |

EO/ビーコン/Wi-Fi/決済は6属性を埋めて登録するだけで追加（媒体プロファイル＝横断軸Bと同思想）。

### シグナルの役割階層

| シグナル | 測定する量 | 精度 | 役割 |
|---|---|---|---|
| 運用型広告（メタ等） | 配信・CV | 高（媒体申告で歪む） | 推計の軸 |
| 人流（LM社） | 来店の量 | 高・5分粒度 | 来店推計の主軸 |
| 決済 | 購買単価・実額 | 最高 | 成果の錨（あれば最優先） |
| 販促CP | 個人購買 | 高・一部 | 来店→購買の個人裏取り |
| ビーコン | 店内行動の質 | 中・低カバレッジ | 来店の質の補強 |
| Wi-Fi | 来店者数 | 中 | 人流の補完・検算 |
| EO（衛星） | 競合店・外形 | 低・雲欠測 | 競合補助・人流の検算 |

同じ量を測るシグナルは検算し合い、違う量なら掛け合わせる（人流の量×決済の単価＝売上）。

### 信頼度加重の推計コア

- **重みの決め方**: 精度×カバレッジ×鮮度を基礎点とし、真値に近いシグナル（決済・ジオリフト）で動的較正（論点Bの較正を全シグナルに一般化）。
- **同量シグナルの統合**: 信頼度加重平均＋相互検算。一致で信頼度UP、食い違いはデータ品質レイヤー（実装詳細3）に警告（突合②クロスバリデーションの一般化）。
- **欠損時の挙動**: ベイズ推計で最小1シグナルから動作。シグナルが少なければ事前分布（業種ベンチマーク）に引っ張られ信頼区間が広く、増えるほど観測尤度が勝って締まる。「読み込めば精度が上がる」の数理的実体＝Meridianのベイズ枠組みそのもの。

### 統一推計モデルの一般式（何でも入る数式の骨格）

EC・広告・人流・物流・POS等、あらゆるシグナルを1つの推計に乗せるための一般形。成果を複数要因の和で説明し、新シグナルは項を足すだけで入る。

```
成果[unit, t] = ベースライン[unit]
              + Σ_媒体 メディア効果(spend)     ← 入力型シグナル
              + Σ_外部 外部シグナル効果         ← 状態型シグナル（人流・天候・物流在庫…）
              + 季節・トレンド
              + 誤差
（結果型シグナル＝POS・決済は右辺でなく左辺の観測尤度を縛る。後述）
```
`unit`=階層の最小単位（地域/店舗/EC全体）、`t`=時間。右辺の項をシグナル種類で増やせる。

#### シグナルの3型分類（一般化の鍵）

すべてのシグナルは成果への効き方で3型に分かれ、型が数式上の位置を決める。

| 型 | 効き方 | 数式上の位置 | 例 |
|---|---|---|---|
| **入力型（driver）** | 成果を能動的に生む・逓減する | adstock＋飽和を通す項 | 広告投下、広告的販促 |
| **状態型（state）** | 成果が起きやすい環境を作る | 線形 or 変調項 | 人流、天候、競合(EO)、物流在庫 |
| **結果型（outcome proxy）** | 成果そのものに近い観測 | 観測尤度の錨 | POS売上、決済、来店実数 |

型判定はシグナル抽象化層の「測定する量」属性から決まる。**新シグナルが来たら型を判定するだけで数式上の位置が自動的に決まる**＝モデルを設計し直さない。これが「EC・広告・人流・物流・POSが1つに繋がる」の数理的実体。

#### 結果型シグナル（POS・決済）の特権的扱い

結果型は他と対等に足さず、モデル全体の錨にする。
```
推定成果[unit,t] ≈ POS実績[unit,t]   ← 結果型は答え合わせの基準（左辺の観測尤度を強く拘束）
```
POSがあるunit・期間ではモデル推定がPOS実績に合うよう全パラメータが拘束され、無い所は推定で埋める。**一部のPOSが全体のモデルを正しい高さに引き上げる**（ジオリフト較正と同じ構造）。

#### 状態型シグナルの入り方＝人流の3経路の一般化

人流で確立した3経路（経路A統制変数／B変調／C媒介）は、実は**状態型シグナル一般の入れ方**だった。だから天候も物流在庫も同じ3経路で入る。
- 物流在庫の例：経路A「在庫があると売れる」／経路B「在庫潤沢な店舗では広告が効く（品切れで広告が無駄にならない）」／経路C「広告→来店→在庫消化」。人流と同形。

#### 多重共線性への対策

シグナルが増えると相互相関で効果を奪い合う（人流・POS・広告は当然相関）。対策：型の役割分担（入力/状態/結果で数式上の位置が違い同項内の奪い合いを構造的に減らす）＋ベイズ正則化（事前分布で各効果を安定化）。Meridianのベイズが効く。

#### 決定事項（統一推計モデル一般式）

1. 成果＝ベースライン＋入力型効果＋状態型効果＋季節＋誤差の一般式。新シグナルは項を足すだけ。
2. 全シグナルを3型分類：入力型（広告・逓減あり）／状態型（人流・天候・物流在庫・環境）／結果型（POS・決済・成果の真値）。
3. 型判定はシグナル抽象化層の「測定する量」属性から。型が決まれば数式上の位置が自動決定。
4. 結果型は右辺の項でなく左辺の観測尤度を縛る錨（一部POSが全体を正しい高さに引き上げる）。
5. 状態型は人流の3経路（A統制/B変調/C媒介）で入る＝状態型一般の入れ方。物流在庫も同形。
6. 多重共線性は型の役割分担＋ベイズ正則化で抑える。
7. 全体がMeridianのベイズ階層に乗る（入力型=メディア項、状態型=control＋相互作用、結果型=観測尤度事前情報）。

### 人流をMeridianにどう注入するか（新規性の心臓部・状態型シグナルの具体例）

Meridianは「地域×時間の売上を、地域×時間のメディア投下で説明する」モデル。人流は広告でも売上でもない**第三のもの（中間）**で標準の枠に素直に入らない。これが「世界の誰もやっていない」理由であり、xADの独自性の核。注入経路は3つあり役割で使い分ける。

#### 経路A：統制変数（コントロール）— 初期標準・最も安全

```
売上[g,t] = ベースライン + メディア効果 + β×人流[g,t] + 季節 + 地域効果
```
人流が「広告以外の来店要因（天候・イベント・季節）」を吸収し、残りを広告の純粋効果としてMeridianが推定。広告効果の推定が精緻になる。Meridianの control variables 機能にそのまま乗る。第一歩。

#### 経路B：媒体効果の地域補正 — 中核の独自性

```
メディア効果[g,t] = adstock_飽和(spend) × (1 + γ×人流偏差[g])
```
同じ広告費でも人通りの多い商圏では来店転換が起きやすい、という相互作用。**広告効果を人流で変調（modulate）**。「どの地域に広告を厚くすべきか」が人流考慮の配分になり、L3-1エリア間配分（穴#3段階2）と直結。Meridian標準にない拡張＝人流統合の核心。

#### 経路C：媒介変数（メディエーター）— 将来・最も野心的

広告効果を「直接効果」と「間接効果（来店経由）」に分解する媒介分析（mediation analysis）の標準形。

```
人流[g,t] = a₀ + a₁×広告[g,t] + 状態統制 + 誤差₁      ← 広告が人流を生む
購買[g,t] = b₀ + b₁×人流[g,t] + c×広告[g,t] + 誤差₂   ← 人流と広告が購買を生む

間接効果（来店経由）= a₁ × b₁
直接効果（来店非経由）= c
総効果 = a₁×b₁ + c
```

「広告費1円が来店経由で何円、直接で何円の購買を生むか」を分解。突合②の整合性スコアが見ていたものを因果モデルとして正式化。O2O二重接続の理想形。

実装上の難所：
- **難所1 因果方向**: 「広告→人流→購買」の順序が前提。逆や交絡で壊れる。**ジオリフトで因果方向を担保**（実験で広告を操作し下流で人流→購買が動くことを確認）。経路A/Bの内生性対策が経路Cでは因果方向の実験的裏付けに昇格。
- **難所2 同時推定**: 2式を別々に推定すると媒介変数の内生性でバイアス。**ベイズで同時推定**（Meridianを構造方程式モデル的に拡張、標準を超えるため経路Cが必要な段階で実装）。
- **難所3 直接効果の解釈**: cには本当の直接効果（オンライン購入）と測定できていない媒介経路が混ざる。**「来店非経由（内訳不明分を含む）」と正直にラベル**、過大にオンライン購入と解釈しない（精度開示）。

価値：経路Cはチャネル設計レベルの示唆（「来店経由8割→店舗体験投資」「直接購入主→オンライン導線強化」）を出す。L3-1配分の一段上、マーケ戦略への示唆。ただしデータ要求・因果仮定が強く、実装優先度は最後＝データと検証が揃った顧客向け最上位機能。

#### 設計判断

- **判断1 採用順**: 段階導入。A統制変数（初期標準）→B地域補正（中核）→C媒介（将来）。全部一度は過学習リスク。少データで動く思想をモデル構造にも適用。
- **判断2 前処理**: 生の人流（5分粒度GPS）は不適。LM社側で**地域×日次に集計→ベースライン偏差に正規化**してから注入（横断軸A-2のL0オフライン版の正規化を流用）。経路Bの相互作用項では絶対値だと地域規模に引っ張られるため偏差が必須。
- **判断3 内生性（最重要）**: 経路Bで「広告効果が人流で変わる」とするとき、広告自体が人流を増やしている場合、人流は独立変数でなく結果。無視すると因果が循環しバイアス。**ジオリフトで対照エリア（広告停止）の人流を見て、人流のうち広告由来でない自然部分を分離**。GeoLift×Meridian連携が内生性対策として効く＝両方持つxADの独自強み（単独MMMツールでは実験検証できない）。経路Cへの布石。

#### 決定事項

1. 人流注入3経路：A統制変数（来店要因吸収）／B媒体効果の地域補正（広告効果を人流で変調・中核）／C媒介変数（広告→人流→売上の因果分解・将来）。
2. 段階導入：A初期標準→B中核→C将来。
3. 前処理：LM社側で地域×日次集計→ベースライン偏差に正規化（横断軸A-2流用）。
4. 内生性対策：ジオリフトで人流の広告由来分を分離（GeoLift×Meridian連携の独自強み）。
5. 経路Bの地域補正がL3-1エリア間配分（穴#3段階2）と直結。

### 経路Bの相互作用項γの推定（多階層・実装の核）

経路Bの式 `メディア効果 = adstock_飽和(spend) × (1 + γ×人流偏差)` のγ（人流が広告効果をどれだけ増幅するか）の推定。素朴にやると3つの落とし穴：(1)γと媒体効果の交絡、(2)地域/店舗数が少なく不安定、(3)内生性（人流が広告の結果でもある循環）。MeridianのベイズとGeoLiftの実験という採用済みの2土台で解く。

#### 多階層（ネスト）でγを持つ

階層は地域で止めず、店舗・クラスタまでネストできる（Meridianの地域階層は元々ネスト想定）。

```
γ_全体     ~ 弱情報事前分布
γ_地域[r]  ~ Normal(γ_全体, σ_地域)        ← 地域は全体の周りに
γ_店舗[s]  ~ Normal(γ_地域[親r], σ_店舗)    ← 店舗は所属地域の周りに
```

- **partial pooling**: 上位で情報共有・下位で個別性。店舗データが薄くても所属地域→全体が支え、**1店舗単位でも推定が壊れない**。データが溜まれば店舗固有γが立つ（少データで動く→賢くなる）。
- **店舗別の打ち手**: 店舗ごとのγが「人流が広告効果を強く増幅する＝広告を厚くすべき店舗」「人流と無関係＝立地で完結」を識別。チェーン経営に実用的。
- **階層の深さは業種・データ量で可変**: 多店舗（薬局/小売）は店舗まで、少数店舗は地域まで。数百店舗は**店舗クラスタ（商圏属性・規模）を中間階層**に（穴#3クラスタリングと連動）。全体→クラスタ→店舗。
- **ビーコン（店舗内ゾーン）は主階層に入れず質的サンプルに留める**（横断軸Aビーコンの役割と一貫）。深くしすぎてデータが耐えられない事態を回避。

#### 交絡・内生性対策：ジオリフトをγの事前分布に

落とし穴1（交絡）と3（内生性）を同じ武器で解く。ジオリフト実験結果をγのinformative priorに注入：
```
1. ジオリフト：人流の高い地域/店舗 vs 低い所で、同じ広告増分の効果差を実測
2. その効果差 = γの実験的証拠（因果的にクリーン）
3. これをγ_全体の事前分布に入れる
4. Meridianが日次データでγ更新するとき、実験事前分布が交絡・内生性を抑える錨に
```
実験（クリーン）が観測（交絡しうる）を錨で固定する。MMM業界標準「実験でMMMを較正」の人流相互作用項への適用＝誰もやっていない一点。

#### 過学習防止と店舗異質性

- σ_地域/σ_店舗に弱情報事前分布。データが階層差を支持する時だけ下位γが分岐（薄いうちは上位に縮約）。
- 店舗属性（規模・立地タイプ・客層）は**共変量で吸収**し、γ階層はその残差（店舗固有の癖）を捉える。役割分担で過学習防止。

#### 決定事項（経路Bγ推定）

1. γを多階層ベイズで推定（全体→地域→店舗、数百店舗はクラスタを中間に）。partial poolingで小サンプル安定化、1店舗単位でも壊れない。
2. ジオリフト実験をγのinformative priorに注入し交絡・内生性を抑える（実験が観測を固定、GeoLift×Meridianの独自強み）。
3. σにペナルティで過学習防止（データが支持する時だけ下位γ分岐）。
4. **γ=0を許す**（人流が広告効果を変調しない可能性を正直に出す、精度開示）。
5. 人流偏差は地域/店舗の平常時平均からの偏差（経路A正規化と統一、時間内変調を捉える）。
6. 店舗属性は共変量で吸収、γ階層は残差を捉える（過学習防止）。
7. γの実験事前分布は四半期ごと再較正（論点B較正サイクルと統一）。
8. 階層の深さは業種・データ量で可変。ビーコン粒度は主階層に入れず質的サンプル。

### 各シグナルの入り方（POS・決済・物流・EC）

一般式の3型分類に沿い、主要シグナル固有の癖と注入を定義。どのシグナルも「型判定→固有の罠に対処→所定の位置に入る」の同手順。

#### POS（結果型・最重要だが繊細）

- **広告由来分の分離**: POS売上は広告由来＋日常購買を全部含む。そのまま広告成果にすると過大評価。POSは目的変数（左辺）であって広告効果（右辺一項）ではない。モデルが「POS全体のうち広告で説明できる部分」を分離。
- **部分カバレッジ**: 一部店舗・期間のみ。POSがあるunitはモデル推定をPOS実績に合わせ、ない所は人流・広告から推定（一部が全体を引き上げる）。
- **タイムラグ**: POSは即時、広告CVは帰属窓ぶん遅れる。L0統一帰属窓に揃えてから突合。

#### 決済（結果型・POSとの役割分担）

POS＝店舗の全売上（量＋単価・マクロ錨）、決済＝個人に紐づく購買（単価・LTVのミクロ追跡）。両方あればPOSで店舗全体を錨にしつつ決済で個人購買を追う。決済は突合③（CRM/LTV）に接続。二重接続（集団×個人）が結果型内でも反復。

#### 物流（状態型または結果型・文脈依存）

| 物流データ | 型 | 注入 |
|---|---|---|
| 在庫量 | 状態型 | 経路A/B（在庫があると売れる、潤沢だと広告が効く） |
| 出荷量 | 結果型 | 売上の代理錨（D2C/卸で実売上が見えない時の成果プロキシ、後でPOSに差し替え） |
| 入荷・補充タイミング | 状態型（イベント的） | 季節・プロモと同様の外部要因 |

- **在庫の内生性（罠）**: 品切れ（在庫ゼロ）だと広告を打っても売れず広告効果がゼロに見えるが、これは在庫制約であって広告が効かないのではない。**在庫ゼロ期間は広告効果の推定から除外 or 制約フラグ**。無視すると品切れ多発店の広告効果を過小評価。経路Bの地域補正の裏返し。

#### EC（入力型と結果型の両方を持つ）

- EC購入CV = 入力型の広告が生む成果（L0統一CVで配分）
- EC売上額 = 結果型の錨（決済と同様）

ECは広告ボードと推計エンジンの境界。メタのみボードならL0で完結、販促ボード（実店舗も持つEC）なら推計エンジンでオンラインEC売上＋実店舗POSを統合。ボード選択エンジンの広告タイプ分岐が効く。

#### 決定事項（各シグナルの入り方）

1. POS：目的変数として広告由来分を分離、部分カバレッジは「ある所だけ錨」、L0統一帰属窓で突合。
2. 決済：個人単位でPOS（店舗マクロ錨）と役割分担、突合③のミクロ追跡に接続。
3. 物流：在庫=状態型（経路A/B）、出荷量=結果型（売上代理錨、後でPOS差し替え）、在庫ゼロは広告効果推定から除外（品切れの内生性）。
4. EC：購入CV=入力型成果（L0配分）＋売上額=結果型錨。メタのみはL0完結、販促はエンジンで店舗POSと統合。
5. 結果型の優先順位：決済＞POS＞出荷量。複数あれば相互検算（突合②一般化）、食い違いはデータ品質警告。
6. 型は「シグナル×業種」で決まる（出荷量はD2C=結果型/小売=状態型）。抽象化層に業種別型マッピング（適用マトリクス拡張）。
7. 補完ポリシーは型依存：結果型は補完しない（錨が推定値だと意味がない）、状態型は補完可。精度開示の一貫。

### 精度評価・検算（推計の自己点検）

推計値の信頼度を測れないと「精度を正直に開示」が空文句になる。精度は1数字でなく3種を区別。

| 精度の種類 | 問い | 測り方 |
|---|---|---|
| 当てはまり（fit） | 過去をどれだけ再現できるか | R²、MAPE |
| 予測力（holdout） | 未知データをどれだけ当てるか | 時系列クロスバリデーション |
| 因果妥当性（causal） | 推定効果は本物の因果か | ジオリフトとの突合 |

**罠**: 当てはまり良好≠正しい。過去に完璧フィットは過学習で予測力が低い。3種を別々に評価、特に因果妥当性を重視（MMM作法）。

#### 3層の検算

- **検算1 ホールドアウト（予測力）**: 直近数週を隠して訓練→隠した期間を予測して当てる。時系列なので**時間順分割**（過去で訓練→未来を予測）必須。
- **検算2 ジオリフト突合（因果妥当性・xAD独自）**: モデル推定の「Metaの効果」と、ジオリフト実験の「Metaの増分」を突き合わせ。一致=因果裏付け、乖離=モデルを疑う。論点Bの較正は「実験でモデルを直す」、検算は「実験でモデルを検査する」。**同じジオリフトが較正・内生性対策・因果検算の3役**。
- **検算3 シグナル間相互検算**: 同量シグナル（人流・Wi-Fi・EOの来店量）の一致チェック。一致=信頼度の証拠、乖離=データ品質警告（突合②一般化、実装詳細3と統合）。

#### 推計値に信頼度を付けて出す

```
推計の信頼度 = f(予測力, 因果妥当性, シグナル一致度, データ量)
  高：ホールドアウト良好＋ジオリフト一致＋複数シグナル一致
  中：一部が弱い（実験未実施、シグナル少）
  低：当てはまりのみ（予測・因果の裏付けなし）
```
全推計値に「点推定＋信頼区間＋信頼度ラベル」（横断軸E統一表現レイヤーの共通フォーマットを推計出力に適用）。「この数字をどれだけ信じていいか」が常に併記＝精度開示の数理的完成形。

#### 決定事項（精度評価）

1. 精度を3種に区別（当てはまり／予測力／因果妥当性）。当てはまり良好≠正しいを明記。
2. 検算1ホールドアウト：時間順分割で予測力検証。
3. 検算2ジオリフト突合：モデル推定効果と実験増分を突合（xAD独自）。同じジオリフトが較正・内生性・検算の3役。
4. 検算3シグナル間相互検算（突合②一般化、データ品質と統合）。
5. 全推計値に点推定＋信頼区間＋信頼度ラベル（横断軸E共通フォーマット）。
6. ジオリフトは必須でなく加点、なければ「因果未検証」明示（少データで動く）。
7. 信頼度「低」は出すが警告し、L3-2アクション優先度の確信度に流し込む。
8. 予測力を毎週モニタリング、誤差閾値超で再訓練アラート（学習ループの推計版）。

### 既存部品の再位置づけ

本エンジンはゼロからの新機能でなく、既存部品を束ねる上位概念。各部品は「シグナル統合」という1操作の特殊例だった。

- L0統一CV → 「広告シグナル」の内部統合
- 突合①（人流量×決済単価）→ シグナル掛け合わせの一例
- 突合②クロスバリデーション → 同量シグナルの相互検算の一例
- ジオリフト較正 → 高信頼シグナルによる較正の一例
- L3-1レスポンスカーブ → Meridianのadstock＋飽和に準拠

### 決定事項

1. 広告タイプで処理系統を分岐：メタのみ=既存L0-L4、販促ボード=本推計エンジン（ボード選択エンジンの拡張）。
2. 技術土台＝Google Meridian（MMM）＋GeoLift（ジオリフト）。車輪の再発明を避ける。
3. 独自部分＝人流をMeridianの地域シグナルとして注入（世界未踏）。
4. シグナル抽象化層（6属性メタデータ）で全入力を統一受信。EO/ビーコン/Wi-Fi/決済は登録だけで追加（横断軸Bと同思想）。
5. シグナルを役割階層化（軸/主軸/錨/補強/補完/補助）。同量は検算、異量は掛け合わせ。
6. 信頼度加重はMeridianのベイズpriorsで実現。真値近接シグナルで動的較正（論点B一般化）。
7. 最小1シグナルから動作、増で信頼区間が締まる（少データで動く→賢くなる）。
8. 既存部品（L0/突合/ジオリフト較正/レスポンスカーブ）を本エンジンの構成要素として再位置づけ。
9. 本番サーバー=Meridian(Python)、ブラウザ=結果表示（既存の負荷配分に一致）。
10. 新規性＝「広告計測×フィジカルセンシングの架橋」「人流統合は世界未踏」「日本販促文脈は国内空白」。

### 数理サマリー（数式の集約・実装早見表）

推計エンジンの全数式を一箇所に集約。実装者はここを参照すれば数理を一望できる。

**① 統一推計モデル（一般式）**
```
成果[u,t] = ベースライン[u]
          + Σ_m メディア効果_m(spend[u,t,m])        # 入力型
          + Σ_s 状態型シグナル効果_s(signal[u,t,s])   # 状態型
          + 季節[t] + トレンド[t] + ε[u,t]
制約：結果型シグナル（POS/決済）は左辺の観測尤度を拘束 → 推定成果[u,t] ≈ POS実績[u,t]
```

**② メディア効果（入力型・adstock＋飽和）**
```
メディア効果_m(spend) = β_m × Hill( adstock(spend) )
Hill(x) = Vmax × x^n / (K^n + x^n)        # 飽和（Meridian準拠）
adstock(spend_t) = spend_t + λ × adstock(spend_{t-1})   # 残存効果
```

**③ 状態型シグナルの3経路（人流・物流在庫など）**
```
経路A（統制）: + β_s × signal偏差[u,t]
経路B（変調）: メディア効果 × (1 + γ_u × signal偏差[u,t])
経路C（媒介）: signal[u,t] = a0 + a1×広告 + ε1
              成果[u,t]   = b0 + b1×signal + c×広告 + ε2
              間接効果 = a1×b1, 直接効果 = c, 総効果 = a1×b1 + c
```

**④ 経路Bの係数γ（多階層ベイズ）**
```
γ_全体   ~ 弱情報事前分布（ジオリフト実験をinformative priorに）
γ_地域[r] ~ Normal(γ_全体, σ_地域)
γ_店舗[s] ~ Normal(γ_地域[親r], σ_店舗)
signal偏差 = (signal[u,t] − 平常時平均[u]) / 正規化       # 偏差ベース
```

**⑤ ジオリフト（増分・iROAS）**
```
合成対照: min Σ_t (treat_pre[t] − Σ_i w_i·control_i_pre[t])²  s.t. Σw_i=1, w_i≥0
          → ASCM（Ridge augmentationで脱バイアス）
増分[t] = treat_post[t] − Σ_i w_i·control_i_post[t]
iROAS = (Σ_t 増分[t] × 来店単価) / 広告費      # 来店単価は突合①のk補正後
較正係数 = 実証iROAS / カーブ予測ROAS           # L3-1へ還元（時間減衰・四半期再較正）
```

**⑥ 検出力（power analysis・配信前）**
```
MDE = (z_{α/2} + z_β) × σ_diff × √(1/N_treat + 1/N_control)
σ_diff = std( treat_pre[t] − control_pre[t] )      # 介入前差分の標準偏差
期間補正: σ_diff / √(T × 0.7)                       # 自己相関の保守的ディスカウント
```

**⑦ 突合（二重接続）**
```
突合①: 増分売上 = 増分来店 × (CP応募者単価 × k),  k = 全来店者単価 / CP応募者単価
突合②: 整合性 = r_cp / r_flow   （正常帯 業種別、帯外は診断シグナル）
```

**⑧ 信頼度加重統合**
```
推計 = Σ_s w_s × シグナル推計_s / Σ_s w_s
w_s = 精度_s × カバレッジ_s × 鮮度_s × 実績較正_s     # 真値近接シグナルで動的較正
欠損時: ベイズ事前分布（業種ベンチマーク）に縮約、シグナル増で観測尤度が優勢→区間が締まる
```

**⑨ 精度評価**
```
信頼度 = f(予測力[holdout], 因果妥当性[ジオリフト突合], シグナル一致度, データ量)
出力フォーマット = 点推定 ± 信頼区間 ＋ 信頼度ラベル{高/中/低}   # 横断軸E共通
```

> 記号: u=最小単位(地域/店舗), t=時間, m=媒体, s=シグナル, r=地域, w=重み。実装は本番サーバーでMeridian(Python)＋GeoLift、ブラウザは⑥の検出力プレビューと結果表示。

## L0: 統一CV定義（最優先・全層の土台）

### 解く問題：二重計上

同じ1コンバージョンを各媒体が別々に計上する。

| 媒体 | デフォルト計測 | 帰属窓 |
|---|---|---|
| Meta | クリック＋ビュースルー | 7日クリック＋1日ビュー |
| Google | クリック（データドリブン可） | 30日クリック |
| TikTok | クリック＋ビュー | 7日クリック＋1日ビュー |
| Yahoo | クリック | 30日 |

例：1人がMeta動画を見て→Google検索クリックで購入すると、Metaは「ビュースルーCV 1」、Googleは「クリックCV 1」と**同一購入を二重計上**。単純合算は実購入数を超過し、横断比較・配分最適化が全て破綻する。

### 判断1：真のCV母数（Single Source of Truth）

媒体の自己申告CVを足さず、唯一の真実を外側に置く。

- **理想形（A）**: 自社実測ベース。GA4 purchaseイベント／自社DBの実購入数を母数として固定し、各媒体CVは「母数をどう奪い合うか＝貢献度」として再配分する。
- **現実的初期値（B）**: 媒体CV合算＋重複補正。各媒体CVを足し、推定重複率で割り引く（媒体APIのみで実現可）。
- **フォールバック規則**: 自社DB/GA4未連携時、またはオフライン業種（葬儀の電話問合せ等）で母数が取れない場合は B を使用。UIに「重複補正済み（推定）」と精度を明示開示する。

> 設計思想：分析精度を謳う製品として、推定の確からしさを常に正直に開示する。

### 判断2：帰属窓の統一

- 製品として**統一クリック帰属窓**を1つ定める（標準30日、業種で可変）。
- 全媒体のCVをこの窓で再計算してから比較する（Metaの7日窓とGoogleの30日窓を並べても比較にならないため）。
- **ビュースルーCV**（見ただけ・クリックなし）は主要KPIから外し、「アシスト/参考値」として別枠で分離表示する。完全に捨てると認知系媒体（動画/ディスプレイ）を過小評価するため残す。

### 判断3：アトリビューションモデル

1購入の功績を複数接点に配分し、二重計上を解く。

| モデル | 配分 | 評価 |
|---|---|---|
| ラストクリック | 最後の接点に100% | 単純／認知系を過小評価 |
| 線形 | 全接点均等 | 公平／大味 |
| 減衰 | 購入に近い接点ほど重く | 直感的 |
| データドリブン | 実データから貢献度を統計推定 | 最精緻／要データ量 |

- **初期標準**: 減衰モデル（ラストクリックより公平、データドリブンより軽い）。
- **昇格**: データが溜まったらデータドリブンへ。L2レスポンスカーブと同じ「少データで動く→賢くなる」思想で一貫させる。

### L0 決定事項まとめ

1. 真の母数 = 自社実測（A）を理想、媒体CV合算＋重複補正（B）をフォールバック、精度をUI開示
2. 帰属窓 = 統一窓（標準30日・業種可変）に再計算、ビュースルーは参考分離
3. アトリビューション = 減衰モデル標準 → データドリブン昇格

## L3-1: 予算配分最適化（差別化の核）

### 基本思想：限界ROAS均等化

既存ツールがやる「平均ROASが高い媒体に寄せる」は罠。逓減（diminishing returns）のため、ROASが高い媒体ほど追加投下で飽和する。正しい問いは「**追加の1円を入れたとき、どの媒体が一番成果を生むか＝限界ROAS**」。

> 最適配分の条件：すべての媒体で限界ROAS（最後の1円の効果）が等しくなる点。

### 統合目的関数（オンラインCVとオフライン来店の統一）

成果が複数種類（オンラインCV・店舗来店）ある業種では、単位の違う成果を足せない。唯一の共通単位＝金額で統一する（L0「単位を揃えてから比べる」の成果版）。

```
統合成果（円） = Σ ( 各成果タイプの件数 × その成果の価値 )
  オンラインCV → 1件あたりの価値（粗利 or LTV）
  店舗来店     → 1来店あたりの価値（突合①の補正後来店単価 × 粗利率）
```

供給元はすべて既存部品：来店価値=突合①キャリブレーション、CV価値=オンボーディングQ1、LTV換算=実装詳細2。新規計算なし。

この統合により、L3-1は「オンライン専業（EC/B2B）」「来店専業」「両方（薬局/飲食）」を**同一アルゴリズム**で処理。違いは「どの成果タイプに円価値が設定されているか」だけ。業種でロジックを分岐させない。

#### 決定事項（統合目的関数）

1. 統合目的関数 = Σ(成果件数 × 円価値) を最大化。異なる成果を金額で統一。
2. 来店価値=突合①、CV価値=オンボーディングQ1、LTV換算=実装詳細2が供給（既存部品で完結）。
3. 円換算は段階化：初期は主成果1つ、複数成果換算は任意のフェーズ2。未設定なら件数ベース単一成果にフォールバック。
4. ダブルカウント防止：成果に階層（来店→購入は購入価値で計上、突合③が紐付け）。L0二重計上回避の来店版。
5. 成果タイプごとにデータソースが違う（オンライン=カーブ＋較正、オフライン=ジオリフト直接）が、円換算で同一最適化に統合。
6. 結果、L3-1は全業種を同一アルゴリズムで処理（設定で吸収、ロジック共通）。

### レスポンスカーブ（投下額→成果の曲線）

データ量に応じてモデルを自動切替する。ユーザーには見せず内部処理。

| 状態 | データ条件 | モデル | 補足 |
|---|---|---|---|
| コールド | 媒体別日次 < 30点 | べき乗（業界bを事前分布に） | 自社データ不足を業界知見で補う |
| ウォーム | 30〜90点 | べき乗（自社データでフィット） | bを実データ推定 |
| ホット | 90点以上＋飽和の兆候 | Hill関数 | 飽和上限Vmaxを推定 |

- べき乗モデル: `成果 = a · spend^b`（0<b<1）
- Hill関数: `成果 = Vmax · spend^n / (K^n + spend^n)`
- 媒体別の指数bデフォルト（少データ時の事前分布）: 検索広告 ≈ 0.5（顕在層・飽和しやすい）、ディスプレイ/動画 ≈ 0.7（潜在層・伸びしろ大）
- 設計思想：少データでも何か返す、データが増えたら賢くなる。

### 目的変数・成果定義はオンボーディングで取得

「何を最適化するか」は意思の問題なのでユーザーに聞く。「指数bはいくつか」は技術前提なので聞かず自動推定する。この切り分けを厳守する。詳細はオンボーディング設計セクション参照。

### 制約条件（数学的最適を現場の打ち手にする）

| 制約 | 内容 | デフォルト |
|---|---|---|
| 媒体別上下限 | 「Metaは最低¥X維持」「新媒体は上限¥Y」 | オンボーディング取得、未設定なら現状±50% |
| 総予算モード | 固定（同予算で組替）/ 可変（限界ROASが閾値超なら増額） | オンボーディングで取得 |
| 急変ガード | 1媒体あたり前期比の変動上限（学習リセット回避） | ±30%/週 |
| 最低出稿量 | 媒体アルゴリズム学習に必要な最低imp/CV | 媒体別に内蔵 |

### 2モード提案（毎日触りたくなるUXとの両立）

急変ガードを強くすると安全だが「大胆な提案が出ずつまらない」。トレードオフを2モードで解決：
- **通常モード**: ±30%の安全な漸進提案
- **攻めモード**: 制約を緩めた理想配分を併記

ユーザーが選択。安全と刺激を両立させる。

### ソルバー実装：逐次配分（貪欲法）

ブラウザ完結前提。1円（実装上は適切な単位）ずつ限界ROASが最大の媒体へ配分し、制約に当たった媒体は除外して継続。

- べき乗/Hillは限界ROASが単調減少 → 貪欲法で大域最適に到達することが数学的に保証される。
- 配分過程（「次の1万円はGoogleへ→限界ROAS逆転→次はMetaへ」）がそのままユーザーへの説明になる。
- グリッド探索（媒体数増で爆発）・勾配法（JS実装が重い）より優れる。

### 出力UX：数字でなく意思決定を見せる

1. 現状 vs 推奨の Before/After（媒体別バー比較＋合計成果予測の差分を1行で）
2. 感度の明示：「Metaを¥30万増 → CV +12件（信頼区間 ±4）」と幅つきで
3. 理由の言語化：L3アクション生成（LLM）に接続。「Metaは飽和に近く限界ROASが低下、Googleはまだ伸びしろあり」

### レスポンスカーブの入力CV（アトリビューションとの接続）

レスポンスカーブの成果軸に使うCVは、**L0で確定したアトリビューション後のCV**（減衰モデル→データドリブン）を用いる。媒体の生CVでなく配分済みCVを使う理由は、生CVは媒体間で二重計上され、カーブが過大にフィットするため。アトリビューションモデルを切り替えるとカーブの入力も変わるので、**カーブ推定時はアトリビューションモデルを固定**し、モデル変更時はカーブを再フィットする（オンボーディングの「目的変数変更時カーブ再フィット」と同じ規則）。

### ジオリフト較正（実験結果のカーブへの統合）

レスポンスカーブ（連続・頻繁・媒体管理画面ベースで歪む）とジオリフトiROAS（離散・疎・真の増分で正しい）は時間粒度も性質も違う。競合させず役割分担する。

- **カーブ = 形（相対）**: 日次データからカーブの曲がり方・飽和点を常時推定。
- **ジオリフト = 高さ（絶対）の較正アンカー**: カーブの絶対水準を真値へ引き上げ/引き下げる目盛り。

ベイズ較正の流れ：
```
1. 日次データでカーブ推定（形＝b/Vmax、事前分布あり）
2. ジオリフト完了で点(spend*, 真の増分成果*)を観測
3. この点を強い尤度としてカーブをベイズ更新（実験点を通るよう較正）
4. 較正係数 = ジオリフト実証iROAS / カーブ予測ROAS を保持
5. 次の実験まで較正係数でカーブ予測を補正し続ける
```
ジオリフトは「カーブ予測がどれだけ楽観的すぎるか」の目盛り。管理画面が iROAS 3.0 でもジオリフトが 1.8 なら較正係数0.6でカーブを現実に引き戻す（Meta iOS計測欠損で管理画面CVが過少な場合は逆に引き上げる方向にも効く）。

#### 決定事項（ジオリフト較正）

1. カーブが「形（相対）」、ジオリフトが「高さ（絶対）の較正アンカー」。役割分担し競合させない。
2. ベイズ更新で実験点をカーブに刺し、較正係数（実証iROAS÷カーブ予測ROAS）を保持して次の実験まで補正。
3. 較正係数は時間減衰（実験直後は強く、経過で素のカーブへ戻る）。次の実験で再較正（L1-1時間減衰と同思想）。
4. 実験した媒体のみ較正、未実験媒体は素のカーブ＋推定バッジ（弱い参考適用は任意）。
5. 来店型業種ではジオリフトが較正でなくカーブの主データになる（業種で切替、論点C／実装詳細5に接続）。
6. カーブ入力CVはアトリビューション後のCV（生CV不可）。アトリビューションモデルはカーブ推定時固定、変更時は再フィット。

## L1: 診断層（Why）

### L1-1: 異常検知

「毎日触りたくなる」要件の本体＝変化の検知。鳴るべき時だけ鳴る精度が要る（オオカミ少年化を避ける）。

#### 現状の限界

実物AAAAダッシュボードは `cpc > 平均×1.3` の単純閾値。問題：曜日変動を異常と誤検知／季節性を無視／緩やかな悪化を見逃す。

#### 3段階の検知ロジック（併用）

| 段階 | 手法 | 捕まえるもの | 重さ |
|---|---|---|---|
| ① ベースライン補正 | 曜日中央値・移動平均からの乖離 | 曜日変動を除いた本当の異常 | 軽 |
| ② 統計的バンド | 移動平均±2σ（頑健にはMAD）を逸脱 | 統計的に珍しい値 | 軽〜中 |
| ③ トレンド検知 | 直近N日の回帰傾き＋連続性 | じわじわ悪化（傾向） | 中 |

単発スパイク（②）とじわ悪化（③）は別物なので両方必要。①曜日補正を土台に乗せる。

#### 決定事項

1. **MADベースの頑健な検知**を採用。広告データは外れ値が多く、平均±σは外れ値に引っ張られて鈍る。MADは外れ値に強く、外れ値を見つけたい用途に合う。
2. **好転も検知**する。CVR急騰日は「何が効いたか」を知りたい → L1-2寄与度分解・L3横展開の入口。悪い知らせだけだと毎日触りたくなくなる。
3. **監視指標の階層化**：
   - 常時監視（能動通知）: CPA、ROAS、CV数（採算に直結）
   - 参照監視（鳴らず色で示す）: CTR、CPM、CVR、フリークエンシー（原因分析用）
4. **業種別パラメータ**に「曜日プロファイル」「季節係数」を持たせ、業種ごとに何を異常とみなすかを変える（葬儀=突発スパイクが正常、EC=セール周期、ウェディング=季節性大）。横断軸の具体的中身。

---

### L1-2: 寄与度分解

#### 解く問題

異常検知が「CVが20件減った」と鳴った次の問い「なぜ？」に答える。ここが弱いとユーザーは手作業でフィルタを切り替え原因を探すことになる。毎日触りたくなる肝は「問いの次に答えが用意されていること」。

#### 2方向の分解（併用）

- **① 次元分解（どこで起きたか）**: CV増減を媒体/キャンペーン/クリエイティブ/オーディエンス/地域/デバイスに割り振る。「CV-20のうちMeta-15、Google-3、TikTok-2」→ Meta内ドリルダウン「-15のうち動画A-12」。
- **② 要因分解（何が変わったか）**: `CV = imp × CTR × CVR` の乗法構造を分解し、imp減少なのかCTR悪化なのかCVR悪化なのかを切り分ける。「imp維持だがCVR悪化が主因」→ LP側の問題、「imp減のみでCVR健全」→ 予算/入札の問題。

①は場所、②はメカニズムを答える。組み合わせて初めて打ち手が決まる。

#### 決定事項

1. 次元分解＋要因分解の2方向を併用。
2. 要因分解は**対数差分分解（log-change）**を採用。軽量かつ加法的に綺麗（各要因の寄与の和が全体変化に一致）。
3. 基準期間は**前週同曜日比をデフォルト**、ユーザー切替可（前日比/期間平均比）。L1-1の曜日補正と思想を揃える。
4. 異常検知が鳴った指標のみ、寄与の大きい順に**Top3を自動提示**。以降は任意ドリルダウン。通知の質と計算負荷を両立。

#### UI接続

アラート「CV-20件」→ タップ →「Meta動画Aが-12件、うちCVR悪化が主因」を一段で表示。L3アクション生成（LLM）はこの分解結果を入力に打ち手を書く。

---

### L1-3: 統計的有意差

#### なぜ製品の看板になるか

「高い分析精度を誇る」を一目で実感させる機能。多くのツールは数字を並べるだけ。クリエイティブA（CPA ¥1,200, CV 8件）vs B（CPA ¥1,400, CV 150件）で、Aの優位はたまたまかもしれない。少件数の数字を過信させないガードレール＝L0「少数CV媒体を過信させない」約束の実装。

#### 判定対象と手法

- **① 比率系（CVR, CTR）**: 試行回数があるので比率差を扱える。**ベイズ的アプローチ**で「AがBに勝つ確率87%」と出す（p値より直感的）。ブラウザ完結ではベータ分布のモンテカルロサンプリングで軽量に勝率算出。
- **② コスト効率系（CPA, ROAS）**: 連続値なので**信頼区間／ブートストラップ**で「CPAは¥1,100〜¥1,750の幅」と示す。幅が重なれば差は誤差範囲と一目で分かる。

#### 決定事項

1. 比率系はベイズ的「勝率」表示、コスト系は信頼区間/ブートストラップ。
2. **「有意/非有意」の二択を捨てる**。勝率を3段階の行動指示に翻訳：「Aが有利（勝率87%）＝行動可」「材料不足（勝率60%・要サンプル）＝待て」「ほぼ互角（勝率52%）＝どちらでも」。
3. **サンプル不足を能動警告**：結果より先に「まだ結論できません（必要CV: あと約N件）」を提示。運用者が「もう3日待とう」と動ける。
4. 効かせる場所を限定：クリエイティブ比較（CREATIVE GRID）／媒体比較（CHANNEL TABLE）／施策前後比較の3箇所のみ。常時全数計算しない。

#### L0・L3との接続

- L0「少数CV媒体を過信させない」「精度をUI開示」をここで実装。
- L3配分最適化の出力「Metaを¥30万増→CV+12件（±4）」の **±4** はこの層が供給。配分提案が幅つきで誠実になる。

---

### L1-4: クリエイティブ疲弊検知

#### 解く問題

同じ広告を出し続けるとターゲットが見飽きて反応が落ちる（広告疲弊）。運用で最頻の劣化要因だが日次変動に紛れて気づきにくい。CREATIVE GRIDの器に乗せる。予兆から実害までタイムラグがあるため、予兆段階で「差し替え時」を教えれば先回りでき、毎日触りたくなるUXに寄与。

#### 疲弊のシグナル組み合わせ

単一指標では誤検知。固有の同時進行パターンで捉える。

| シグナル | 疲弊時 | 単独だと紛らわしい理由 |
|---|---|---|
| フリークエンシー | 上昇 | 配信が進めば自然に上がる |
| CTR | 低下 | 単純な不調と区別つかない |
| CPM | 上昇 | 市況でも上がる |
| CVR | 低下/横ばい | 他要因でも動く |

**決定的パターン = フリークエンシー上昇 × CTR低下 の同時進行**。CPM上昇が加われば確定。組み合わせと時間的持続で判定。

#### 決定事項

1. フリークエンシー上昇×CTR低下の同時進行を中核に、CPM上昇で確定。単独でなく組み合わせ＋持続で判定。
2. **絶対閾値でなく相対劣化**で見る（業種/媒体で正常値が違うため）。そのクリエイティブ自身の初期性能を基準に「配信2週間のCTRから30%低下、かつフリークエンシー上昇」。各広告が自分の過去と戦う。
3. **3段階予報**：🟢健全（初期性能維持）／🟡兆候（フリークエンシー上昇開始・CTR微減＝差し替え準備推奨）／🔴確定（CTR明確低下・CPM上昇＝差し替え必須）。🟡の予兆で予告するのが価値。
4. **寿命予測**（現ペースだと約N日後に採算割れ）は段階実装。初期は3段階判定のみ、データ蓄積後にL2予測層と連動。
5. 検知を起点にL3へ接続：🔴→アクションカード化、勝ち要素（L1-3把握）をLLMに渡し修正案、好調広告（L1-1好転検知）は横展開とセット。悪い知らせで終わらせない。

## L3-2: AIアクション生成（製品の頭脳）

### 解く問題

L1の検知は「事実の指摘」止まり。ユーザーが欲しいのは「で、何をすればいい？」。完成済みのアクションカードUI（優先度＋タグ＋インパクト＋実行/保留/却下）に中身を供給する。「示唆の更新＝毎日触りたくなる」のもう片翼。

### 現状の課題

実データ（AAAA）は閾値ルールで動的生成（萌芽あり）、業種別は完全ハードコード（「LinkedInの予算を+30%」が固定文字列）。これをL0〜L2の分析結果を入力に動的生成する統一エンジンへ置き換える。

### 3層構造（ロジックとLLMの分業）

LLMに丸投げすると根拠の薄い提案が出る。ロジックが「何を提案すべきか」を決め、LLMは「どう伝えるか」だけを担う。

- **第1層 トリガー（ロジック）**: 各検知結果がアクションの種を生む。L1-1悪化→原因調査、L1-1好転→横展開、L1-4疲弊🔴→差し替え、L3-1→再配分、L1-3有意差→勝ち広告ブースト。
- **第2層 優先度付け（ロジック）**: high/med/lowを「**インパクト×確信度×緊急度**」スコアで機械決定。インパクト=動くCV/金額（L3-1予測）、確信度=統計的裏付け（L1-3勝率/信頼区間）、緊急度=悪化速度（L1-1トレンド傾き）。
- **第3層 言語化（LLM）**: 確定した「何を・なぜ・どれだけ」を運用者に刺さる日本語へ。ここで初めてClaude API。

### 決定事項

1. 3層構造：トリガー（ロジック）→優先度付け（ロジック）→言語化（LLM）。
2. **LLMは翻訳に限定**。数値判断（提案選定・優先度・インパクト試算）は全てロジック。理由：(a)数値をLLMに計算させると幻覚、(b)再現性、(c)CORS制約。`window.__scriptedReply`フォールバックパターンで実装（デモ=scripted、本番=サーバー経由）。
3. 優先度 = インパクト×確信度×緊急度のスコアで機械決定。
4. **効果検証ループ**：実行したアクションを後日自動追跡し「3日前の再配分→CPA -12%確認」と返す。提案しっぱなしにしない。実物「✓実行済み」を検証まで拡張。
5. **カード構造化スキーマを固定**（UI側との接続契約）:

```
{
  priority: "high|med|low",        // 第2層スコアで決定
  category: "予算|クリエイティブ|計測|配信",
  title: "...",                    // LLM言語化
  reason: "...",                   // LLM言語化（根拠を翻訳）
  impact: { metric: "CV", delta: +12, ci: 4 },  // L3-1+L1-3供給
  confidence: 0.87,                // L1-3供給
  source: "L3-1",                  // 生成元（追跡用）
  verification: { status: "pending|confirmed", result: "..." }
}
```

6. **業種別パラメータにアクション優先度の重み**を持たせる（葬儀=緊急枠取りこぼし最優先、EC=在庫×ROAS、薬局=O2O来店）。

---

### L3-3: クリエイティブ修正提案

#### 解く問題

L1-4が疲弊🔴を検知、L3-2が差し替え推奨をカード化。次の壁「どう直せばいい？」に答える＝要件「AIで修正も行う」の中身。多くのツールは「差し替えろ」で終わる。

#### 修正提案の3レベル

| レベル | 内容 | 実現性 |
|---|---|---|
| L1 診断的修正 | 何が悪いか特定し改善方向を示す | 高（ロジック＋LLM文章） |
| L2 要素提案 | コピー・訴求軸・構成の具体案をテキストで | 中（LLM生成） |
| L3 ビジュアル生成 | 画像/動画そのものを生成 | 低（別系統・将来） |

**L1・L2を本仕様の射程**とし、L3ビジュアル生成は将来拡張に切り離す（別API・コスト・著作権配慮が絡み分析ロジックと別レイヤー）。

#### 中核ロジック：勝ちパターンを保ちつつ変える

1. **勝ち要素の特定（ロジック）**: L1-3で有意に勝つクリエイティブの共通属性を抽出（訴求軸/フォーマット/人物有無/テキスト量/CTA文言）。
2. **負け要素の特定（ロジック）**: 疲弊・低performの共通点。
3. **LLMへ構造化入力**: 「勝ち=情緒訴求×人物あり、負け=長文、疲弊=動画A」という事実を渡し改善案を生成。LLMは判断せず言語化のみ。

#### 決定事項

1. L1診断的修正＋L2要素提案を射程、L3ビジュアル生成は将来拡張。
2. 勝ち/負け要素をロジックで抽出 → LLMは事実を言語化するだけ（判断させない）。「何が勝ちか」を推測させると外す。
3. クリエイティブのメタデータ：媒体APIで取れるもの（フォーマット/サイズ）は自動取得、取れないもの（訴求軸/トーン）はオンボーディング/手動タグ、将来は**画像をLLMに解析させて自動タグ付け**（base64でAPI送信）。
4. 提案は**次のA/Bテスト案とセット**で出し、L1-3有意差判定へループバック。言いっぱなしを防ぎ製品が学習。
5. **業種別パラメータに訴求軸の辞書**（葬儀=安心/誠実、ウェディング=憧れ/特別感、EC=お得/限定）を持たせLLM入力に加える。

#### UI接続

CREATIVE GRIDで広告選択 → 「AI修正提案」展開 → 勝ち要素可視化＋改善コピー案＋A/Bテスト設計。生成はscripted/mock、本番サーバー経由。

### L3-4: 競合・ベンチマーク示唆

#### 解く問題と現実

要件「競合の状況を鑑みた打ち手」。ただしデータソースに厳しい現実がある。

| データソース | 取得可否 | 見える/見えない |
|---|---|---|
| Meta広告ライブラリ / Google透明性センター | 公開・取得可 | 出稿・クリエイティブは見える / **効果（CPA等）は見えない** |
| 業界ベンチマーク（媒体CPM/CVR） | API・外部 | 業界平均は取れる / 個社実数は取れない |
| 自社の過去パターン | 内部 | 全部見える（最も確実） |

**決定的事実：競合の「効果」は原理的に取得不可**。「競合のROASを見て対抗」は作れない／作ると嘘になる。

#### 3つの示唆（確実な順）

- **示唆① 自社×業界ベンチマーク乖離（主軸・最確実）**: 「CVRが業界平均を20%下回る→LP改善余地」。L1-3で乖離の有意性も付与。ベンチマークは出典明記。
- **示唆② 競合クリエイティブ動向（補助・限定）**: 広告ライブラリから出稿傾向を捉える。効果は見えないが市場トレンド（「競合が動画＋価格訴求に集中」）は読める。LLMが「追随か差別化か」の論点提示に使う。効果データ無しを正直に開示。
- **示唆③ 自社内相対ベンチマーク（確実・見落とされがち）**: 自社ベストperformを基準に他キャンペーンの伸びしろ。競合データ不要。「キャンペーンXのCVR 4.2%を他が達成したらCV+N件」。

#### 決定事項

1. 競合の「効果」は取得不可を起点に設計。誇大表現を避ける。
2. ①自社×業界乖離（主軸）／②競合クリエイティブ動向（補助・将来）／③自社内相対（確実）の3段。
3. 「競合の効果を当てる」とは言わず「**市場トレンド×自社ポジショニング**」と位置づける。できないことを正直に線引きする方が信頼される。
4. ベンチマークは**出典明記**（デモは内蔵データ、本番は外部API）。メモリ原則：ベンチマーク統計はソースを示す。
5. ②競合クリエイティブ取得はサーバーサイド前提の将来機能（規約配慮）。①③を初期主軸、②はデモでscripted。
6. 数値はロジック算出、LLMは論点への翻訳のみ（L3-2/L3-3と同じ分業）。

## L2: 予測層（What will happen）

### L2-1: 着地予測

#### 解く問題

月の途中で「今のペースだと月末にどこへ着地するか」。運用者・マネージャー双方が毎日気にする問い。月末の駆け込み調整を防ぐ。毎日更新され昨日と変わるので「毎日触りたくなる」にも効く。

#### 2つの着地を予測

- **① 予算消化の着地**: 月末までに使い切るか/余らせるか/オーバーか。線形外挿では不正確（配信は曜日波・予算制限で非線形）。L1-1の曜日プロファイルで残日数の消化を予測。
- **② 成果（CV/売上）の着地**: 目標CVに届くか。単純外挿の罠＝月後半に予算が尽きると配信もCVも止まる。①と連動させ「予算が23日で尽きる→以降CV発生せず→着地N件で未達」まで示す。

#### 決定事項

1. 「予算消化の着地」と「成果の着地」の2軸、両者を連動（予算切れ→CV停止を織り込む）。
2. **曜日波を考慮した補正外挿**。重い時系列モデル（ARIMA等）は使わずブラウザ完結を維持。
3. 予測は必ず**信頼区間付き**（点予測の罠を避ける）。L1-3の思想を継承。
4. 段階性：初期は曜日補正外挿 → 成熟でトレンド成分追加。L0・L3-1と一貫した「少データで動く→賢くなる」。
5. 着地予測を**L3-2アクションに接続**（未達ペース→予算前倒し、オーバーペース→入札抑制）。

### L2-2: レスポンスカーブ推定

L3-1予算配分最適化の中核として確定済み（べき乗→Hill自動切替、媒体別事前分布、データ量による状態遷移）。詳細はL3-1参照。

**統合整理**: 着地予測（時間軸の予測）とレスポンスカーブ（投下額軸の予測）は同じ予測エンジンの2つの出力。実装上は共通の「予測モジュール」として基盤化する。

## 横断軸A: オフライン統合（人流分析・ビーコン）【LocationMind社協業】

> **※適用条件（ガード）**: `industry.useFootTraffic === true` の場合のみ。false の業種では本セクション全体（AREA MAP / O2O FUNNEL / ジオリフト）を実装・表示せず、関連アクション（`source: "geolift"`）も生成しない。適用可否は実装詳細5の適用マトリクスに従う。

### 位置づけと協業前提

広告接触→来店→購買のオフラインまで繋ぐ層。薬局・ポップアップ・ウェディング等の来店型業種で決定的差別化。地図のL3最終形。実物にAREA MAP/BEACON LOG/O2O FUNNELの器あり。

**データソースはLocationMind社（LM社）との協業で確定。** LM社が人流データを供給、addashが広告データとの統合・因果分析・配分還元を担う。役割分担：LM社=人流の供給と一次集計、addash=広告との突合・分析・可視化・打ち手提案。

> **穴#8：単一障害点リスク**。人流レイヤー全体がLM社に依存するため、LM社のデータ仕様変更・価格改定・提供停止が人流機能を止める。緩和策：(1)人流データI/Oを抽象化レイヤーで受け、将来別プロバイダ（unerry等）に差し替え可能な構造にする、(2)人流が止まってもオンラインL0-L4は独立して動く（ボード選択エンジンが人流レイヤーをグレーアウトするだけ）。人流は「あれば強化」であり「無いと全停止」にはしない。

### LM社データの特性と設計含意

| 特性 | 内容 | addash設計への含意 |
|---|---|---|
| 店舗前人流（高精度） | 道路リンク単位でGPS集計、交通モード判別（徒歩/鉄道/クルマ）＋マップマッチングで店舗前通行量を高精度推定 | ジオリフトの処置群/対照群を**道路リンク＝店舗前通行量**で組める。来店分析に理想的粒度 |
| 粒度 | 125m/250mメッシュ＋道路リンク、属性（性別/年代）あり | 広告ジオターゲティングをこの粒度に合わせ、配信と人流を同一座標系で突合 |
| 匿名・統計加工 | ドコモアプリ利用者の許諾済み位置情報を統計加工、個人特定情報を含まない。最短5分ごと測位 | 「個人を繋がず集団で見る」設計とデータ性質が完全一致。プライバシー前提がLM社側で担保 |
| 提供形式 | CSV/Webダッシュボード、カスタム集計、顧客データ取り込み可 | LM社のCSV/APIを入力に広告データと突合する層をaddashが担う |

**5分粒度GPSの強み**: 「14時に配信ブースト→夕方に店舗前通行増」という時間内ラグ相関まで見える。日次集計のツールより広告→来店の時間的因果に迫れる。ただし5分生データのブラウザ処理は重いため、**LM社側で必要粒度に集計したものを受け取り、addashは分析・可視化に専念**。

### O2O接続の壁の正体（3層）

「広告と来店が繋がらない」は3つの壁の重なり：
- **壁① ID接続（個人レベル）**: 広告を見た人と来店した人を個人で繋ぐのはプライバシー規制下で原則不可。→ **越えず迂回する**（集団の同期で見る）。
- **壁② 時間遅延**: クリックは即時、来店は数日後。→ ラグ付き相関で吸収（LM社5分粒度が効く）。
- **壁③ 増分（因果）**: 「広告がなくても来店したのでは？」→ **ジオリフトで正面から解く**。

### 二重接続モデル（本ソリューションの核）

O2Oの壁を「上（集団・因果）」と「下（個人・実購買）」から挟み撃ちにする。

- **上位接続（集団・因果）= ジオリフト**: LM社人流で処置群/対照群エリアの差から広告の純増分を算出。業界標準の合成コントロール（synthetic control）で介入前トレンドを再現し、介入後の差を増分に帰属。ランダム化不要・少地域数で機能・遡及分析可でブラウザ完結に乗せやすい。指標は **iROAS（増分売上÷広告費）**。
- **下位接続（個人・実購買）= 販促CP**: クローズドCP（レシート/シリアル）とCRM連携CP（LINE）で購買を個人IDで裏取り（横断軸D参照）。

ジオリフトが集団で増分を出し、クローズド/CRM CPが個人で購買を裏取りする。この組み合わせが他社にない統合の絵。

### 3段階の統合レベル

- **統合① 時間相関分析（最確実・第一歩）**: 広告配信量とLM社人流の時間相関。5分粒度でラグ相関まで。O2O FUNNELの土台。
- **統合② ジオリフト（因果・本丸）**: 道路リンク/メッシュ単位で処置・対照を組み、合成コントロールで増分来店・iROASを算出。
- **統合③ 店内行動×広告訴求（質的・将来）**: ビーコンのゾーン滞在と広告訴求を結ぶ。SHELF RANKING/FLOOR PLANの器に対応。

### ビーコンの役割

**量は人流（LM社）、質はビーコン**で役割分担。ビーコンは来店者のうちアプリ起動＋Bluetooth ONの数%しか捕捉できずカバレッジが低いため、母数にはせず**店内動線の質的サンプル調査**に限定。

### ジオリフト実験設計ロジック（上位接続の心臓部）

**本質**: ジオリフトは実験であり、配信後では取り返しがつかない。実験設計ロジックの役割は「配信前にこの設計なら検出できると保証すること」。設計の質が結果の質を決める。以下4判断で構成。

#### 判断1: 処置群／対照群エリアの選定

成否の8割。対照群が処置群の「広告を打たなかった場合」を正しく代弁できるかが核心。単なる近接・人口類似でなく、**介入前トレンドの類似性**（合成コントロールの発想）で選ぶ。

| 選定軸 | 内容 | LM社データの活用 |
|---|---|---|
| トレンド相関 | 介入前N週の人流推移の相関が高い | 道路リンク単位の時系列で相関算出 |
| 規模の同等性 | 通行量の絶対水準が近い | 店舗前通行量で正規化 |
| 属性の類似 | 性別・年代構成が近い | LM社の属性データ |
| 地理的独立 | 処置群の広告が漏れない距離 | **交通モード判別でエリア間の行き来を測りスピルオーバー防止** |

- **スピルオーバー防止が独自の強み**: 処置/対照が近すぎると処置エリア向け広告が対照住民にも届き対照群が汚染される。LM社の交通モード判別（徒歩/鉄道/クルマ）で「両エリア間の人の行き来」が分かるため、行き来が少ないペアを選べる。他社にない選定。
- **判断1A**: 製品が候補ペアを自動提案、運用者が業務都合（出店予定等）で調整するハイブリッド。

#### 判断2: 必要サンプルサイズと実験期間（検出力分析）

「何エリア×何週間で検出したい効果を捕まえられるか」を**配信前に計算（power analysis）**。判断1と並ぶ核心価値。

1. 検出したい最小効果（MDE: Minimum Detectable Effect）を決める（例「来店+5%」）
2. 人流のばらつき（分散）を過去データから推定
3. 必要エリア数・期間を逆算（例「+5%を検出力80%で捕まえるには処置10×対照20×4週間」）

- **判断2A**: MDEは運用者が答えにくいため**予算からの逆算で提示**。「予算¥Xなら検出できる最小効果は+Y%、これより小さい効果は誤差に埋もれる」と予算×検出力のトレードオフを可視化。判断3に直結。

#### 判断3: 最低出稿額

少なすぎると人流に変化が出ず検出不能（ジオリフト最大の失敗パターン）。規定する3要素：

- **処置エリアの配信密度**: 来店行動を動かすに足るリーチ×フリークエンシー
- **エリア数×期間**: 判断2の検出力から
- **ベースライン来店の変動幅**: 元の人流のブレが大きいほど多くの予算が要る

- **判断3A**: 最低出稿額を「**保証ライン**」として出し、「この予算では検出不能なのでやめましょう」と止める機能を持つ。無駄な実験を防ぐ誠実さ＝L0「精度を正直に開示」の実験版。「¥30万では+15%以上の巨大効果しか見えません。最低¥Xが必要」と事前提示。
- 相場観：ジオターゲ広告の配信最低額は50万円〜（Location AI例）。ただし配信最低額とジオリフト検出力に必要な額は別物。

#### 判断4: 効果の検定（結果の出し方）

**手法**: 合成コントロール＋反実仮想の比較。対照群から「処置群が広告を打たなかった場合の人流（反実仮想）」を構築し、実際との差を増分とする。信頼区間で有意性を示す。

- **判断4A**: 表示はL1-3の哲学を継承。p値二択でなく「増分来店 +12%（95%CI +4%〜+20%）、iROAS 1.8」と幅つき。行動指示翻訳「効果は確実（区間が0を十分上回る）／判断保留（区間が0をまたぐ）」。
- **判断4B**: **プラセボテスト内蔵**。対照エリア同士で偽の実験を回し「効果がないはずの所に効果が出ないこと」を確認。結果の信頼性が跳ね上がる。分析精度を誇る製品として推奨。

#### 一気通貫ループへの接続

出力iROASは終点でなく**L3-1配分最適化の入力に還る**。「Metaのジオリフトで iROAS 1.8、Googleで 2.4 →Googleの限界ROAS評価を上方修正→次期配分をGoogleに寄せる」。実験が配分を更新し次の実験へ。学習ループ（横断軸C-⑤）のO2O版の具体形。

#### 決定事項

1. エリア選定：介入前トレンド相関＋規模同等＋属性類似＋地理的独立（交通モード判別でスピルオーバー防止）。候補自動提案＋運用者調整。
2. 検出力：配信前power analysisで必要エリア数×期間を逆算。MDEは予算からの逆算で提示。
3. 最低出稿額：配信密度×エリア数期間×ベースライン変動で規定。「検出不能なら止める」保証ラインを出す。
4. 検定：合成コントロールで反実仮想を構築し信頼区間で増分提示。L1-3の行動指示翻訳を継承。プラセボテストで頑健性チェック内蔵。
5. 出力iROASをL3-1配分最適化に還す一気通貫ループ。

### 射程：測定で終わらせず一気通貫ループへ

測定だけのツール（unerry/Location AI等）は飽和市場。addashの差別化は**ジオリフト実験の設計→運用→測定→配分還元の一気通貫ループ**。製品が実験設計（テスト/対照エリア選定、最低出稿額、期間）を提案し、結果をL3-1配分最適化に還す。学習ループ（横断軸C-⑤）のO2O版。

### 決定事項

1. データソースはLM社で確定。LM社=人流供給、addash=統合・分析・可視化・打ち手。
2. ジオリフトの処置/対照は**道路リンク＝店舗前通行量**で組む（LM社の高精度粒度を活用）。
3. 二重接続モデル：上位=ジオリフト（集団・因果・iROAS）、下位=販促CP（個人・実購買）。
4. 統合①時間相関（5分粒度ラグ相関）→②ジオリフト（合成コントロール）→③店内行動（将来）の3段。
5. 量は人流、質はビーコン。ビーコンは母数にせず質的サンプルに限定。
6. 5分生データはLM社側で集計受領、addashは分析・可視化に専念（ブラウザ完結維持）。
7. 統合KPIは **iROAS（増分ベース）** と **O2O ROAS（推定来店価値込み）**。推定は精度開示、オンラインROASと分離表示可。
8. 射程は測定でなく実験設計→運用→測定→配分還元の一気通貫ループ（測定ツール飽和市場での差別化）。
9. L0〜L3を貫く拡張として接続（来店をCV定義に追加、人流の異常検知、配分に来店含める、エリア来店好調→配信増額アクション）。
10. デモはscripted、本番はLM社CSV/API連携。統合①時間相関を第一歩に。

## 横断軸A-2: オフラインデータへの各層適用（L0〜L3のオフライン版）

> **※適用条件（ガード）**: `industry.useFootTraffic === true` の場合のみ。横断軸Aと同条件。

L0〜L3はオンライン広告前提で設計した。LM社人流という新データ型に対し、既存ロジックの何が流用でき何が固有かを切り分ける。全層を作り直さない。

### L0オフライン版：人流の「統一」問題

- **CV相当の定義**: 店舗前通行は「店の前を通った人」であり入店ではない。**通行 ≠ 来店 ≠ 入店**を区別。LM社の滞留/通過データで切り分ける。
  - 通行 = 来店ポテンシャル
  - 滞留（一定時間その地点に留まる）= **来店相当（主指標）**
  - 入店 = 最深指標（POS/ビーコン/販促CPが取れる時のみ）
- **正規化**: エリアごとに元の通行量が桁違い（都心店/郊外店）。絶対数でなく**ベースラインからの変化率**で揃える（L1-1曜日補正と同じ思想）。

### L1オフライン版：最も固有性が高い

- **L1-1 異常検知（人流版）**: オンラインの曜日補正は流用可。ただし人流固有の交絡（天候・気温・近隣イベント・曜日祝日）が激しく効く。広告と無関係な「雨で来店減」を異常と誤検知すると無意味。**天候・気温を必須でベースラインに組み込んでから乖離を見る**。天候は人流最大の交絡。イベントは段階実装（初期は手動注記、将来は自動）。
- **L1-2 寄与度分解（人流版）**: オンラインの`imp×CTR×CVR`に相当する人流版＝`来店 = 商圏人口 × 商圏内通行率 × 通行者の入店率`。来店減が「商圏の人が減った（外的）」のか「通ったが入らない（店舗の問題）」のかを切り分ける。突合②クロスバリデーションと連動（広告で通行増だが入店率低下を捉える）。

### L2オフライン版

着地予測は流用しやすい。月内来店ペースから月末着地を補正外挿で。ただし来店型業種は季節性が強いため**季節係数の重みをオンラインより大きく取る**。

### L3オフライン版

ジオリフト実験設計＋二重接続突合で具体化済み。配分最適化（L3-1）に来店・iROASを組み込む点も決定済み。新規の具体化は少ない。

### 設計判断

- **判断1 外部要因データ**: 天候・気温は必須でL1-1人流版のベースライン補正に組込。近隣イベントは段階実装（手動注記→自動）。
- **判断2 KPIの主軸**: 通行/滞留/入店の3階層。**滞留=来店主指標**、通行=来店ポテンシャル、入店=最深（CP/POS時のみ）。L0統一CVの来店版。

### 決定事項

1. L0：通行/滞留/入店を区別。滞留=来店主指標、通行=ポテンシャル、入店=最深。変化率で正規化。
2. L1-1：曜日補正は流用、天候・気温を必須でベースライン補正に組込（人流最大の交絡）。イベントは段階実装。
3. L1-2：`来店 = 商圏人口 × 通行率 × 入店率`の分解で外的要因か店舗問題かを切り分け（突合②と連動）。
4. L2：着地予測を流用、季節係数の重みを大きく。
5. L3：ジオリフト・二重接続で具体化済み、新規少。

## 横断軸D: 販促キャンペーン（CP）統合

> **※適用条件（ガード）**: `industry.usePromoCPP === true` の場合のみ。下位の突合ロジックは `useFootTraffic && usePromoCPP === true` の場合のみ（片方でもfalseなら突合をスキップし、利用可能な側のみ単独で分析）。適用可否は実装詳細5の適用マトリクスに従う。

### 位置づけ

販促広告にはオープンCP・クローズドCP・CRM連携CP（LINE等）があり、ノベルティが絡む。これらは単なる施策種別でなく、**O2O二重接続モデルの「下位接続＝個人レベルの実購買裏取り」を合法的に担う手段**。広告分析（L0〜L3）と来店分析（横断軸A）を、購買で繋ぐ結節点。

### CP種別とO2Oにおける役割

| CP種別 | 販促上の目的 | O2Oでの役割 | 接続の仕組み |
|---|---|---|---|
| **オープンCP** | 認知・新規リーチ・友だち獲得 | ライトな興味シグナル | 応募と広告接触の時間相関で効果を見る |
| **クローズドCP（マストバイ）** | 購買促進・売上直結 | **購買の直接証明** | 購入が応募条件＝参加者数=購買者数。レシート/シリアルで個人レベルに購買捕捉 |
| **CRM連携CP（LINE等）** | 囲い込み・リピート | **個人IDの合法的な架け橋** | 友だち追加→購買→再来店を同一ID（opt-in済）で追跡 |

### 販促CPファネルの可視化

オープン→クローズド→CRM→再来店をO2O FUNNELの器で一気通貫可視化。例：LINE友だち獲得のオープンCPで集客→対象商品購入のマストバイCPを同一アカウントで実施→囲い込み→再来店、というファネル全体をaddashが可視化。

### 下位接続の突合ロジック（二重接続モデルを閉じる）

#### 突合の本質的難しさ：粒度の非対称

上位（ジオリフト）と下位（販促CP）は同じO2Oを見るがデータ性質が正反対。

| | 上位＝ジオリフト | 下位＝販促CP |
|---|---|---|
| 単位 | 匿名の集団（エリア） | 特定個人（応募者） |
| 母数 | エリア全通行者 | 応募した人だけ |
| 見えるもの | 来店の「増分」 | 購買の「実数」 |
| カバレッジ | 全数 | 一部（応募者のみ） |
| 因果の強さ | 強い（実験で分離） | 弱い（応募者は元々買う気） |

**罠**: 単純に足すと二重計上、単純に比べると母数違いで無意味（L0の媒体間二重計上がオンライン×オフラインで再発）。競合させず**役割を分けて補完**させる。

#### 突合①: キャリブレーション（集団を個人で校正）— 必須の土台

ジオリフトは増分来店を出すが購買額は人流に映らない。販促CPの実購買で校正：
- ジオリフトが処置エリアの増分来店数（集団・匿名）
- 同エリアのクローズドCP応募（=レシート購買）から来店あたり平均購買額を推定（個人・実額）
- 「増分来店 × 実購買単価 = 増分売上」でiROAS精度を上げる

人流が「量」、販促CPが「単価」を供給。二重計上が起きない最も素直な補完。

#### 突合②: クロスバリデーション（2つの増分を照合）— 信頼性レイヤー

販促CP単独でも増分は測れる（クローズドCP応募数の配信/非配信エリア差）。これをジオリフトの人流増分と照合：
- 同方向に動けば結果の信頼性が跳ね上がる（判断4Bプラセボテストと同じ頑健性）
- 食い違えば「人流は増えたが購買応募は増えていない＝来店したが買っていない（店頭の問題）」という**新しい診断**。突合の食い違いがL1診断層の新シグナルになる。単独データでは見えない洞察。

#### 突合③: 個人ファネルの接続（CRM連携の独自価値）— プレミアム

CRM連携CP（LINE）はopt-in済みで個人を時間軸で追える唯一のデータ：
- 広告接触（推定）→友だち追加→初回購買→再来店→リピートを同一IDで追跡
- **LTV（横断軸C-③）の実測値**が取れる。ジオリフトは初回来店増分まで、CRMは生涯価値まで
- ジオリフトのiROAS（即時）とCRMのLTV/CAC（長期）の2軸で配分判断が変わる

ジオリフト=獲得の効率（何人増えたか）、CRM=獲得顧客の質（良い顧客か）。

#### 設計判断

- **判断A 突合の主従**: ①キャリブレーション=必須の土台（iROAS精度に直結）、②クロスバリデーション=信頼性レイヤー、③個人ファネル=CRM連携がある顧客のみのプレミアム。全顧客が販促CPを持つわけではないので「データがある分だけ突合が深まる＝使うほど精度が上がる」構造。
- **判断B 突合の単位を揃える**: ジオリフトは道路リンク/メッシュ、販促CP応募はレシート住所/店舗。販促CP応募を「応募者の居住メッシュ or 購買店舗のメッシュ」にマッピングしLM社人流と同一座標系に乗せる。L0統一CVの「単位を揃えてから比べる」原則の地理版。
- **判断C 欠損時のフォールバック**: 販促CPなし/CRM未連携/住所欠損は頻発。突合データがある部分だけ精度を上げ、ない部分はジオリフト単独iROAS（推定）。**「校正済みiROAS」と「推定iROAS」をUIで区別表示**（精度の正直な開示）。

#### 二重接続モデルの完結

ジオリフトが集団・因果で「増えた」を証明、販促CPが個人・実額で「いくら・誰が」を埋める。食い違いは診断シグナル、CRMはLTVまで伸ばす。すべてが iROAS／LTV として L3-1配分最適化に還りループが閉じる。

#### 決定事項

1. 突合①キャリブレーション：人流が量、販促CPが単価を供給し増分売上・iROAS精度を上げる（必須）。
2. 突合②クロスバリデーション：2つの増分を照合。一致で信頼性向上、食い違いはL1診断の新シグナル。
3. 突合③個人ファネル：CRM連携で広告接触→購買→再来店を同一IDで追いLTV実測（CRM顧客のみプレミアム）。
4. 判断A：①必須／②信頼性／③プレミアムの段階化。データがある分だけ深まる。
5. 判断B：販促CP応募を居住/購買店舗メッシュにマッピングし人流と同一座標系に正規化。
6. 判断C：校正済みiROASと推定iROASをUIで区別表示。

### ノベルティの扱い

CP群の**インセンティブ設計変数**として組み込む。「どのノベルティが応募率・購買転換を上げたか」をA/Bで測定し、L3-3クリエイティブ修正と同じ枠組みで「効くノベルティ」を学習する。

### 決定事項

1. CPを施策種別でなくO2O二重接続の「下位接続（個人・実購買裏取り）」と位置づける。
2. オープン（興味シグナル・時間相関）／クローズド（購買の直接証明・レシート/シリアル）／CRM連携（個人IDの架け橋・LINE）の3種を扱う。
3. オープン→クローズド→CRM→再来店のファネルをO2O FUNNELの器で可視化。
4. ノベルティはインセンティブ変数として効果測定（L3-3と同じA/B学習枠組み）。
5. クローズド/CRM CPの個人レベル購買データと、横断軸Aのジオリフト集団増分を突き合わせ、O2Oを上下から挟み撃ち。

## オンボーディング設計（設定の取得）

### 設計思想

役割は「各分析ロジックが動くために必要な設定を、ユーザーの意思として取得する」。

> **意思は聞く、技術前提は聞かない。** 「何を成果と見なすか」(意思)は聞く。「指数bはいくつか」(技術前提)は聞かず自動推定する。

### 各層が必要とする設定の棚卸し

| 設定項目 | 必要とする層 | 聞き方 |
|---|---|---|
| 成果（CV）の定義 | L0統一CV・全層の土台 | 聞く（意思） |
| 目的変数（CV/CPA/ROAS） | L3-1配分最適化 | 聞く（意思） |
| 目標値（目標CPA等） | L2着地予測・L3-1制約 | 聞く（意思） |
| 媒体別上下限・維持媒体 | L3-1制約 | 聞く（運用都合） |
| 予算モード（固定/可変） | L3-1制約 | 聞く（意思） |
| 業種 | 横断軸・全層パラメータ | 聞く（カタログで選択済み） |
| 来店をCVに含めるか | オフライン統合 | 聞く（来店型業種のみ） |
| レスポンスカーブ指数b | L3-1 | **聞かない（自動推定）** |
| 曜日プロファイル・季節係数 | L1-1異常検知 | **聞かない（学習）** |
| クリエイティブのメタタグ | L3-3 | 一部聞く（取れないものだけ） |

### 段階的オンボーディング（離脱を防ぐ）

- **フェーズ1（起動必須）**: 業種選択（済）／媒体連携（最低1）／成果定義。これだけで暫定モード起動、L0・L1が動く。
- **フェーズ2（後から任意）**: 目的変数・目標値 → L3-1・L2解禁。媒体上下限・維持媒体・予算モード → 配分精度向上。
- **フェーズ3（該当業種・将来）**: 来店をCVに含めるか → オフライン統合。クリエイティブのメタタグ → L3-3精度向上。

機能が段階アンロックされる。「使うほど賢くなる」をオンボーディングでも体験。

> **穴#5：初月体験**。新規は初日データゼロで推定バッジだらけになり離脱リスク。伴走型導入（人がオンボードを支援）を前提とし、初月は「推定値でも意思決定の方向は示す」設計にする。フェーズ1の最小構成（業種＋媒体1＋成果定義）で初日から何か返すことを保証。
> **穴#9：設定サボり対策**。フェーズ2以降の任意設定を永遠に未設定だと統合目的関数（論点C）が件数ベースに留まり配分精度が上がらない。未設定が続く項目は、関連する画面で**能動リマインド**（「目標CPAを設定すると配分最適化が有効化されます」）。フォールバックで動きつつ、設定への導線を出し続ける。

### 質問フロー（最小構成）

- **Q1 成果の定義（L0）**: 購入/申込・問合せ/資料DL・会員登録/アプリインストール/複数。複数時は主従と各成果の価値（円換算）を任意設定→売上ベース最適化解禁。
- **Q2 最適化ゴール（L3-1）**: CV最大化/CPA抑制/ROAS最大化/**目標CPA内でCV最大化**（実務最多）。後者選択時Q2-2「目標CPAは？」。
- **Q3 制約（L3-1）**: 維持したい媒体／上限を抑えたい媒体（任意・スキップ可）。
- **Q4 予算モード（L3-1）**: 固定の組替／成果が出れば増額。
- **Q5 来店（オフライン・業種限定）**: 店舗来店も成果に含めるか。

### 決定事項

1. 「意思は聞く、技術前提は聞かない」を貫く。
2. 段階的オンボーディング（フェーズ1必須で暫定起動、2で最適化解禁、3で拡張）。機能が段階アンロック。
3. 質問はQ1〜Q5の最小構成。
4. 設定はいつでも変更可、目的変数変更時はカーブ再フィット、変更履歴を残す。
5. 自動推定値は理由を開示（精度の正直な開示を一貫）。
6. **業種選択が全パラメータセットを一括ロード**（曜日プロファイル初期値・訴求軸辞書・アクション優先度の重み・KPI定義・ベンチマーク）。入力負荷を最小化。

## 横断軸B: 媒体プロファイル（媒体拡張の設計）

### 設計思想

媒体を1つ増やすたびにロジックを書き換える作りは破綻する。これまでのL0〜L3は媒体非依存で組んできた。その思想を明文化する。

> **媒体を「プラグイン」として扱い、媒体ごとの差異を媒体プロファイル1箇所に閉じ込める。** ロジック本体は媒体名を知らない。プロファイルを追加すれば新媒体が乗る。媒体追加がロジック変更でなく設定追加で済む——横断統合を謳う製品の生命線。

### 媒体プロファイルの構造

各媒体は以下を持つ。Meta/Google/TikTok/YouTube/Yahoo、将来のLINE/X/Criteo等も同一枠組みで追加可能。

| プロファイル項目 | 用途（参照する層） |
|---|---|
| デフォルト帰属窓 | L0で統一窓に再計算 |
| 主目的（認知/獲得/混在） | L3-1レスポンスカーブの性質 |
| 指数b初期値 | L3-1事前分布（検索≈0.5、動画/ディスプレイ≈0.7） |
| 固有指標 | L1参照監視に追加 |
| クリエイティブ形式 | L3-3メタタグ |
| 最低出稿量 | L3-1制約 |

### 媒体別の注意点

- **YouTube**: 「視聴」という中間成果がある。主KPIに入れず視聴系を「アシスト指標」として別枠（L0ビュースルーと同じ扱い）。動画疲弊（L1-4）では視聴維持率の低下が固有シグナル。指数b≈0.7（動画・潜在層）。
- **Yahoo**: 検索とディスプレイが混在。1媒体内で性質が違うため、レスポンスカーブを**配信タイプ別に分けて推定**。L3-1「媒体レベル最適化」の例外として内部を検索/ディスプレイに分割。
- **拡張余地**: TikTok/LINE/X/Criteo等も同じプロファイル定義で後から無限に追加可能。

## 横断軸C: 追加で組み込む6つの考え方

全層を貫く設計観点。すべて正式採用。

### ① データ品質・信頼性レイヤー（L0の下の土台）

全分析はデータが正しい前提で動くが、API遅延・タグ欠損・通貨/TZズレが起きる。「このデータは信頼できるか」を判定する層をL0の下に置く。「Metaのデータが過去2日未取得」「CVタグが3日前から未発火の疑い」を検知し、異常検知（L1-1）が誤発火する前に「データ起因か実態か」を切り分ける。分析精度を誇る製品の隠れた土台。

### ② セグメント別分析（横断軸）

全体CPAが横ばいでも、新規悪化・既存好調で相殺されることがある。新規/既存・デバイス・地域のセグメント軸を分析全体に通す。L1-2寄与度分解の次元に含めたものを「常時意識する軸」に格上げ。特に**新規獲得効率の劣化**は全体平均では見えない最重要シグナル。

### ③ LTV・投資回収の時間軸（戦略レイヤー・段階実装）

ROASは即時売上だが本来見るべきは獲得顧客の生涯価値。CPAだけ見るとLTVの高い優良顧客を逃す。LTV/CACを上位KPIに持つとマネージャー・経営層への価値が跳ねる。即時ROASとLTVベースの2軸で配分が変わりうる。**データ蓄積が前提のため段階実装**（初期は即時ROAS、蓄積後にLTV軸を追加）。

### ④ 予算ペーシング（運用実務直結）

着地予測（L2）の手前で日内・月内の予算配分を平滑化。「月初に使いすぎて月末に枯れる」を防ぐ。着地予測と配分最適化の中間にある、運用者が毎日気にする実務機能。

### ⑤ 学習効果のループ（製品が賢くなる仕組み・差別化の核）

各所の「A/Bテストにループバック」「効果検証」を製品横断の学習ループとして明文化。出した提案→実行→結果を記録し、提案ロジック自体の精度を測る。「addashの提案に従うとCPAが平均何%改善したか」を製品が自己評価。「使うほど賢くなる」の実体であり、毎日触りたくなる根拠。

### ⑥ アラート疲れの制御（UXの裏側）

検知を増やすほど通知過多のリスク。「何を能動通知し、何を黙って色で示すか」を製品方針に。L1-1の階層化に加え、**通知の総量管理**（1日の能動通知は最大N件、重要度でフィルタ）を横断ルールに。毎日触りたくなるは、裏返せば毎日うんざりさせないこと。

### 優先度の整理

- **組み込むべき（土台と差別化の核）**: ①データ品質、⑤学習ループ
- **組み込むと強い**: ②セグメント、③LTV（段階実装）、④ペーシング、⑥アラート制御

## 横断軸E: 統一表現レイヤー（検定の一貫性・穴#2解決）

製品内に有意性判定が複数ある（L1-3＝比率/コスト比較、ジオリフト＝エリア実験）。手法を1つに統一するのは不適切（比率にベイズ、時系列に順列検定が各々最適）。問題は手法でなく「出力表現と行動翻訳がバラバラ」なこと。**検定エンジンは複数・適材適所、表現レイヤーは1つ**に分離する。

### 2階層構造

- **下層：検定エンジン（複数・統一しない）**: 比率比較→ベイズ勝率（L1-3）、コスト比較→ブートストラップ（L1-3）、エリア実験→順列検定（ジオリフト）。各々最適な手法。
- **上層：統一表現レイヤー（1つ）**: どの検定出力も共通の3段階確信度に翻訳してから表示。

```
全検定を「確信度」に正規化：
  高（行動してよい）  ← 勝率>85% / 順列上位5%外 / CIが0を十分外れる
  中（材料不足・待て）← 勝率60-85% / 境界的
  低（ほぼ互角）      ← 勝率<60% / CIが0をまたぐ
```

ユーザーはクリエイティブ比較でもジオリフトでも同じ「高/中/待て」で判断できる。裏の手法は違っても表現と行動指示は1つ。L1-3の行動指示翻訳を全検定共通の上層に格上げ。

> これは「実体は複数・インターフェースは1つ」というxAD共通パターン（媒体プロファイル＝媒体は複数ロジックは1つ、ボード選択＝ボードは複数エンジンは1つ）の検定への適用。新思想でなく既存パターンの再利用。

### 決定事項

1. 検定手法は統一しない（比率=ベイズ、コスト=ブートストラップ、エリア実験=順列検定、各適材適所）。
2. 上層に統一表現レイヤーを1つ置き、全検定出力を共通の3段階確信度（高/中/低＝行動してよい/待て/互角）に翻訳。
3. L1-3の行動指示翻訳を全検定共通の上層レイヤーに格上げ。
4. 「高」の基準を保守的に揃える（どの検定でも偽陽性5%以下を高）。
5. 全検定共通の出力フォーマット＝「点推定＋幅＋確信度ラベル」。

## L4: クリエイティブ生成層（xADのもう一本の柱）

### 位置づけ

xADは「分析ボード選択」と「クリエイティブ自動生成」の2本柱。L4は後者の中核。実物のAAAAボードに AI STUDIO として既に実装が先行（プロンプト生成／テンプレート／A/B自動作成／PNG出力／一覧保存）。本セクションは実装を追認しつつ、分析ロジックとしての裏付け（実データ駆動の予測・学習ループ）を与える。L3-3クリエイティブ修正提案の上位・独立機能。

### 実装済みの現状（追認）

- **生成3モード**: ①プロンプト→文言生成（キーワードマッチ）②テンプレート選択（4種×配色5種）③A/B自動派生（変化軸=全部/見出し/配色/CTA、案数2-4）
- **描画・出力**: Canvas実描画で1080px PNG書き出し、一覧保存、詳細モーダル
- **A/B予測**: 勝ちそう度バッジ＋予想CTR＋差分チップ

メモリ原則（scripted応答・CORS回避・PNG出力）に忠実で、デモ体験は成立済み。

### 強化すべき3点（仕様の出番）

**弱点1: 勝ちそう度が乱数。** 実装は `winScore = 55 + (seed%40)`（文字列長から決定的に出すモック）。これを**実データ駆動の予測**へ。L1-3勝敗判定＋L1-4疲弊＋L3-3勝ち要素抽出を入力に「過去の勝ちクリエイティブの訴求軸と一致する度合い」でスコアを出す。乱数→根拠ある予測。

**弱点2: プロンプト生成がキーワードマッチ。** 5パターン固定分岐。本番はClaude API（サーバー経由）で実生成。**「LLMは翻訳」原則の例外として、L4では「文言・訴求の創造はLLM、テンプレート適用・配色・描画はロジック」と分業**を明文化。生成は翻訳でなく創造なのでLLMの役割が他層と異なる。

**弱点3: 生成→効果→学習ループが未接続。** 生成・保存まではあるが配信後実績へのフィードバックがない。生成物に**メタタグ（訴求軸/テンプレート/配色/CTA型）を付与**し、配信後の実績と紐付け、勝ちパターンを更新。L3-3のA/Bループバックと横断軸C-⑤学習ループに接続。

### 生成ロジックの分業（弱点2の詳細）

| 工程 | 担当 | 配置 |
|---|---|---|
| 文言・訴求軸の創造 | LLM（Claude API） | サーバー（デモはscripted） |
| 勝ちそう度予測 | ロジック（L1-3/L1-4/L3-3駆動） | ブラウザ |
| テンプレート適用・配色・レイアウト | ロジック | ブラウザ |
| Canvas描画・PNG出力 | ロジック | ブラウザ |

### 勝ちそう度予測の本物化（弱点1の詳細）

```
予測スコア = w1 × 訴求軸の過去勝率（L3-3勝ち要素辞書との一致度）
          + w2 × テンプレート/配色の過去実績（L1-3で有意に勝ったパターン）
          + w3 × 疲弊リスクの低さ（L1-4：既存配信と似すぎていないか）
          − ペナルティ（既存クリエイティブとの類似度が高すぎる＝共食いリスク）
```
データが無い初期は業種の訴求軸辞書（L3-3）を事前分布に。蓄積で実績重みを上げる（少データで動く→賢くなる）。予測には信頼区間を付け、L1-3の行動指示翻訳を継承（「勝ち予測（確信度高）」「材料不足」）。

### 生成→効果→学習ループ（弱点3の詳細）

```
生成（メタタグ付与：訴求軸/テンプレート/配色/CTA型）
  → 配信 → L1-3で実績の勝敗判定 → L1-4で疲弊検知
  → 勝ちパターン辞書（L3-3）を更新
  → 次の生成の予測スコア（弱点1）と事前分布が賢くなる
```
これでL4が「使うほど良いクリエイティブを生む」自己改善ループになる。横断軸C-⑤学習ループのクリエイティブ版。

### 決定事項

1. クリエイティブ生成をL3-3付随でなく独立した中核機能（L4）に格上げ。実装（AI STUDIO）を追認。
2. 生成3モード（プロンプト/テンプレート/A/B派生）を維持。
3. 勝ちそう度を乱数から実データ駆動へ：L1-3勝敗＋L1-4疲弊＋L3-3勝ち要素を入力にスコア化。共食いリスクをペナルティに。少データ時は業種訴求軸辞書を事前分布に。
4. 生成ロジックを分業：文言・訴求の創造はLLM（サーバー、デモscripted）、予測・テンプレ適用・描画はロジック（ブラウザ）。「L4では生成=LLM、構成=ロジック」と明文化。
5. 生成物にメタタグ付与→配信実績と紐付け→勝ちパターン更新の学習ループ（横断軸C-⑤のクリエイティブ版）。
6. 予測は信頼区間付き、L1-3の行動指示翻訳を継承。

## 実装橋渡し（UI実装仕様）

### アーキテクチャ階層（穴#10計算量・#11単一HTML肥大化の解決）

「単一HTMLでブラウザ完結」は当初の制約だが、製品がxADプラットフォームに育った今、デモと本番でアーキテクチャを分ける。

| | デモ/プロトタイプ | 本番xAD |
|---|---|---|
| 形態 | ボード単位の単一HTML | 通常Webアプリ（Vite+React+TS） |
| 役割 | 営業・検証・体験 | 実運用 |
| データ | scripted | 実API・LM社連携・サーバー計算 |

- **穴#11解決**：全ボードを1ファイルに詰めるのをやめ、**ボードごとに独立した単一HTML**に分割。ボード選択エンジンがどのボードHTMLを出すか選ぶ。単一HTML原則を保ちつつ（各ボードは単一HTML）肥大化を防ぐ。共通ロジック（L0-L4コア）はCDN配信の共有JSにまとめ各ボードHTMLが読む（CDN可原則の範囲）。
- **穴#10解決**：重い検定（プラセボ/ASCM/DML）はサーバー、ブラウザは検出力プレビュー（軽）＋結果表示のみ。デモは事前計算したscriptedデータで「動いている体験」を提示（AAAAダッシュボードの既存パターン）。
- **二重持ち回避**：デモscriptedと本番実APIはインターフェースを揃えデータソースだけ差し替え（`window.__scriptedReply`パターン全面適用）。

決定事項：
1. デモ/本番でアーキテクチャ分離（デモ=ボード単位単一HTML、本番=Vite+React+TS）。
2. 単一HTMLをボード単位で分割、ボード選択エンジンが出し分け。共通ロジックはCDN共有JS。
3. 重い計算はサーバー、ブラウザは軽い計算と表示のみ。デモは事前計算scripted。
4. デモと本番はインターフェース統一・データソース差し替え（ロジック二重持ち回避）。
5. **穴#12：scripted組合せ爆発対策**。検知×業種×データ充足の全状態にscriptedを用意するのは非現実的。デモは「代表シナリオ」（業種ごと1-2本の典型ストーリー）に絞り、それ以外は汎用テンプレ応答。営業・検証に必要な範囲だけ作り込む。
6. **穴#13：検出力プレビューのキャッシュ**。σ_diff推定が介入前全データ走査を伴うため、エリアdrag操作のたびの再計算は重い。介入前データのσ_diffは初回計算してキャッシュし、エリア選択変更時は該当エリアの差分のみ再計算。

### ジオリフト数理実装（実験設計エンジンの中身）

「ブラウザで動く実験設計エンジン」の計算仕様。理論でなく実装方針。

#### 準拠手法（自前実装でなく確立手法ベース）

ジオリフト＝増分測定は学術・業界で確立した領域。独自実装でなく標準手法に準拠して堅牢性と対外的説得力を確保する。

- **基本線：Meta GeoLift（MITライセンス・オープンソース）準拠**。合成コントロール法（SCM）の最新研究に基づくエンドツーエンド実装で、パワー計算・市場選択・推論を備える。販促広告がMeta前提であることとも相性が良い。
- **SCMの強化：ASCM（拡張合成コントロール）＋ GSC（一般化合成コントロール）**。素のSCMは「処置群を対照群で正確に再現できない（inexact matching）」時にバイアスが出る。ASCMがRidge augmentationで脱バイアス、GSCが小サンプル・異質効果に頑健な推論を担う。本仕様のパート2は素のSCMでなくASCMを採用する。
- **⚠️ 過小評価バイアスの明記（最重要）**: 最新研究によりSCMは効果量を系統的に過小評価することが知られる（非線形性や外的ショック下で顕著）。**ジオリフトのiROASは実際より低く出る可能性がある**。重要局面ではパネルDML（二重機械学習）で検証する二段構えとし、このバイアスをUIに開示する（「精度を正直に開示」の実践）。
- **較正の更新周期**: 市況・季節・チャネル飽和で真のリフトは変動するため、四半期ごとの定期再テストで較正係数を更新（業界標準）。論点Bの時間減衰と整合。

> 以下のパート1〜3は、上記の確立手法をxADのブラウザ完結環境にどう落とすかの実装方針。本番はサーバーでGeoLift/CausalPy相当を回し、ブラウザは検出力プレビューと結果表示の簡易版を担う。

#### 負荷配分

| 計算 | 重さ | 配置 |
|---|---|---|
| power analysis（検出力プレビュー） | 軽 | ブラウザ（リアルタイム更新が要る） |
| 合成コントロール構築（重み最適化） | 中 | ブラウザ（少エリアなら可）/重ければサーバー |
| 効果の検定＋プラセボテスト | 中〜重 | サーバー（順列検定は反復多い） |

#### パート1: power analysis

最小検出可能効果（MDE）：
```
MDE = (z_α/2 + z_β) × σ_diff × √(1/N_treat + 1/N_control)
```
z_α/2=1.96（両側5%）、z_β=0.84（検出力80%）、σ_diff=処置群と対照群の来店指標差の標準偏差、N=エリア数。

**σ_diffの推定**：LM社の介入前データから「平常時に処置群と対照群の差がどれだけブレるか」を測る。
```javascript
function estimateSigmaDiff(treatSeries, controlSeries) {
  const diffs = treatSeries.map((v, t) => v - controlSeries[t]);
  const mean = diffs.reduce((a,b)=>a+b,0) / diffs.length;
  const variance = diffs.reduce((a,b)=>a+(b-mean)**2,0) / (diffs.length-1);
  return Math.sqrt(variance);
}
```
平常時の差分が安定（σ_diff小）なペアほど小さな効果を検出できる＝判断1「介入前トレンド類似性」が検出力に直結する数学的理由。

- **期間T**：観測点増でばらつき低下、素朴には σ_diff/√T。ただし人流は自己相関が強く √T は過大評価。**判断1A：保守的ディスカュント**（√(T×0.7)等）で安全側に。検出力を楽観視して失敗するより厳しめに見て確実に検出（判断3「止める」思想と一貫）。
- **予算変換（判断2A・3）**：予算→1エリア配信額（予算/N_treat）→リーチ率（媒体プロファイルCPMから逆算）→検出可能MDE。「予算¥Xで検出可能な最小効果+Y%」を出し、Yが業種の来店リフト相場を上回るなら「検出不能」赤字警告＝保証ライン。

#### パート2: 合成コントロール構築

対照群を単純平均でなく「処置群の介入前トレンドを最もよく再現する加重平均」で作る。
```
最小化： Σ_t ( treat[t] − Σ_i w_i × control_i[t] )²
制約：   Σ w_i = 1,  w_i ≥ 0
```
制約付き最小二乗（非負・合計1）＝L3-1配分最適化と同じ構造。**射影勾配法**で実装（厳密QPソルバーを避け軽量・説明可能。L3-1貪欲法と同じ思想）。
```javascript
function fitSyntheticControl(treatPre, controlsPre, iters=500, lr=0.01) {
  const n = controlsPre.length;
  let w = new Array(n).fill(1/n);
  for (let k=0; k<iters; k++) {
    const pred = treatPre.map((_, t) =>
      controlsPre.reduce((s,c,i)=>s+w[i]*c[t],0));
    const grad = controlsPre.map(c =>
      -2 * treatPre.reduce((s,tv,t)=>s+(tv-pred[t])*c[t],0));
    w = w.map((wi,i)=>wi - lr*grad[i]);
    w = w.map(x=>Math.max(0,x));                 // 非負化
    const sum = w.reduce((a,b)=>a+b,0);
    w = sum>0 ? w.map(x=>x/sum) : new Array(n).fill(1/n);  // 合計1に正規化
  }
  return w;
}
```
少エリア（数十）ならブラウザで一瞬。**判断2A：過学習防止**＝重みが少数エリアに集中すると介入後に外れる。重み分散にL2正則化、または上限（1エリア0.5まで）。初期は正則化強め。

> **ASCMへの拡張（本番）**: 上記の制約付き最小二乗はSCMの「ベース部分」であり、これ単体ではinexact matchingバイアスが残る。本番ではこの重みづけの後に**Ridge回帰を介入前残差にフィットして反実仮想を脱バイアス**する（ASCM = Augmented SCM）。ブラウザの簡易版は素のSCMで検出力プレビュー用、本番サーバーはASCM（GeoLift/CausalPy相当）でiROAS算出、と役割を分ける。過小評価バイアス（準拠手法参照）が疑われる重要局面ではパネルDMLで併走検証。

#### パート3: 検定とプラセボテスト

増分算出：
```
増分[t] = treat_post[t] − Σ w_i × control_i_post[t]
累積増分 = Σ_t 増分[t]
iROAS = (累積増分 × 来店単価) / 広告費   ← 来店単価は突合①キャリブレーションが供給
```

**プラセボ（順列）検定**：分析精度の肝。
```
1. 対照候補の各エリアを「偽の処置群」に見立て、残りで合成対照を作る
2. 偽処置群の介入後の「見せかけ増分」を計算（本来ゼロのはず）
3. 全対照エリアで繰り返し「効果ゼロ時の増分分布」を得る
4. 本物の増分がこの分布のどこに位置するか → p値相当
```
本物の増分が偽分布の外れ値（上位5%等）なら効果は本物。正規分布を仮定しないノンパラ検定で人流の歪んだ分布に頑健。順列が多いのでサーバー推奨。

- **判断3A 表示**：L1-3継承。「増分来店+12%、偽実験分布の上位3%（≒有意）、iROAS 1.8（CI +1.2〜2.4）」と幅つき＋行動指示翻訳。

#### 全体フロー

```
[設計時] σ_diff推定 → power analysis → MDE/予算プレビュー（ブラウザ・リアルタイム）
[設計時] 合成コントロール重み最適化（射影勾配法・ブラウザ）
[配信後] 増分算出 → プラセボ検定 → iROAS（サーバー）
[還元]   iROAS → L3-1配分最適化の限界ROAS更新
```
すべて既存の設計思想（軽量・制約付き最適化・少データで賢く・精度開示）の延長。新思想は持ち込まない。

#### 決定事項

1. **準拠手法**：自前実装でなくMeta GeoLift（MITライセンス）準拠を基本線。合成コントロールはASCM（拡張SCM）＋GSCで脱バイアス・頑健推論。
2. **過小評価バイアスの明記**：SCMは効果量を系統的に過小評価しうる。重要局面でパネルDML併走検証、UIにバイアス開示（精度の正直な開示）。
3. 負荷配分：検出力プレビューと簡易SCMはブラウザ、ASCM/DML本算出と検定はサーバー（GeoLift/CausalPy相当）。
4. power analysis：MDE式で算出、σ_diffは介入前の処置-対照差分から推定。自己相関は保守的ディスカウントで安全側。
5. 合成コントロール：ブラウザは素のSCM（制約付き最小二乗・射影勾配法）でプレビュー用、本番はASCM（Ridge augmentationで脱バイアス）。過学習防止に正則化/重み上限。
6. 検定：プラセボ（順列）検定でノンパラに有意性判定。L1-3の幅つき＋行動指示表示を継承。
7. 較正は四半期ごとの定期再テストで更新（業界標準、論点B時間減衰と整合）。
8. iROASをL3-1の限界ROAS更新に還す。

#### 粒度ミスマッチの解決（穴#3：実験単位と配分単位）

ジオリフトはエリア（店舗商圏）単位で測り、L3-1配分は媒体単位で振る。両者を繋ぐ中間層「媒体×エリア」を明示する。

- **較正の測定単位 = 媒体×エリア**（処置エリアで動かす媒体を指定すれば測れる）。
- **配分は2段階**：段階1=媒体間配分（全エリアを店舗規模で加重平均した較正を使う、L3-1）／段階2=エリア間配分（較正のエリア差を使い、媒体のジオターゲティングで制御）。
- 同じ較正データを**媒体軸に集約＝段階1、エリア軸に展開＝段階2**に投影。論点Bの較正の投影先が2つある、と整理。

決定事項：
1. 粒度を3層（媒体／エリア／媒体×エリア）に整理。較正の測定単位は媒体×エリア。
2. 配分2段階：段階1媒体間（加重平均較正）、段階2エリア間（較正のエリア差）。
3. 同一較正データを媒体軸集約＝段階1、エリア軸展開＝段階2に投影。
4. 段階1を主機能、段階2は販促タイプボードのみ（広告タイプで配分粒度が変わる、ボード選択エンジンと一貫）。
5. 全店舗で実験せず、店舗クラスタリング（商圏属性・規模）で代表実験→同クラスタに較正を外挿（突合①のk外挿基盤＝穴#4と共有）。

## 実装詳細1: 二重接続の突合の数理

### 突合①キャリブレーション：来店単価の推定

応募者は購買額が高めにバイアス（買う気のある人が応募）。素朴に応募者単価を使うと過大評価。
```
増分売上 = 増分来店数 × 補正後来店単価
補正後来店単価 = CP応募者の平均単価 × バイアス補正係数 k
k = 全来店者の平均単価 / CP応募者の平均単価   ← POSがある時に実測
```
POSのあるエリア・期間で k を実測すれば、POS無しにも外挿。POS皆無なら k を業種デフォルト（保守的 <1、例0.7）で置き推定開示。

> **穴#4：POS有無混在時のk外挿基準**。店舗間で客層が違えばkも違うため、チェーン一律でなく**店舗クラスタリング（商圏属性・規模・客層）でグループ化し、POS店のkを同クラスタのPOS無し店へ外挿**。穴#3のジオリフト店舗クラスタリングと同じ基盤を共有。

### 突合②クロスバリデーション：整合性スコア

```
r_flow = 処置増分来店 / ベースライン来店
r_cp   = 処置エリアCP応募増分 / 非処置エリアCP応募
整合性 = r_cp / r_flow
```
- ≈1：人流増と購買増が一致＝信頼性高
- <1：来店増だが買っていない＝**入店率/店頭転換の問題**（L1-2人流版の入店率低下と一致）
- >1：購買増が来店増を上回る＝客単価上昇 or 計測漏れの疑い

正常帯（例0.7〜1.3）を業種別に持つ。帯外で診断シグナル発火。

### 突合③個人ファネル：座標系の正規化

```
応募者 → 居住地（郵便番号/住所）→ LM社メッシュID
店舗購買 → 店舗座標 → メッシュID
```
郵便番号→メッシュは多対多なので**面積按分または人口按分**で重みづけ（「郵便番号XはメッシュAに0.6、Bに0.4」）。CP応募をメッシュ単位人流と同一座標系で突合。

### 決定事項

1. 突合①：増分売上 = 増分来店 × (CP応募者単価 × k)。kはPOS実測、無ければ業種デフォルト（保守的<1）で開示。
2. 突合②：整合性 = r_cp / r_flow。正常帯（業種別）を外れたら診断シグナル。
3. 突合③：郵便番号→メッシュを面積/人口按分でマッピングし同一座標系化。
4. 突合信頼度スコア（POS有無/応募数/座標解像度）でiROASに高/中/低を付与（判断Cバッジの数値版）。

## 実装詳細2: LTV/CRMモデル

### LTV算出の3段階

| 段階 | 方式 | 式 | 必要データ |
|---|---|---|---|
| 初期 | 簡易LTV | 平均購買単価 × 平均購買頻度 × 平均継続月数 | 数ヶ月の購買履歴 |
| 中期 | コホート逓減 | 月次残存率カーブから累積LTVを積分 | コホート別継続データ |
| 成熟 | 確率モデル(BG/NBD等) | 購買回数と離脱を確率分布で予測 | 個人単位の購買時系列 |

実物のEC dashboardのコホート分析器に中期方式を乗せる。

### CACとの接続（二重接続の真価）

```
CAC = 広告費 / 増分獲得顧客数   ← 増分はジオリフトが供給（純増分）
LTV/CAC比 = 予測LTV / CAC
```
ジオリフトが純増分顧客数を出すからCACが正確。普通のツールは「広告費÷全新規」で広告無しでも来た顧客を含めCACを過小評価する。増分ベースCACはより誠実で厳しい。

### CRMファネルの時間軸モデル

```
各ステージ間：転換率 p_i と 平均遷移日数 d_i
離脱予測：最終購買からの経過日数 > 平均購買間隔 × 係数 → 離脱フラグ
```
離脱予測→L3-2アクション「離脱予兆顧客にCRM施策」（L1-4疲弊検知の顧客版＝予兆段階で打つ）。

### 決定事項

1. LTVは3段階（簡易→コホート逓減→確率モデル）。コホートは実物EC dashboard器に乗せる。
2. CACはジオリフトの増分獲得顧客数から算出（増分ベースで誠実）。LTV/CAC比を上位KPIに。
3. CRMファネルを転換率×遷移日数でモデル化、離脱予測→L3-2アクションへ。
4. LTV予測期間は12ヶ月標準・業種可変（ウェディング=1案件、薬局=24ヶ月等）。
5. 個人単位で計算しセグメント集計で表示（個人を画面に出さない。匿名集計の一貫）。

## 実装詳細3: データ品質・信頼性レイヤーの検知ルール

L0の下の土台。L1-1異常検知が「データ起因の偽異常」で誤発火する前に、データ自体の健全性を判定。

### 4つのデータ異常の検知ルール

- **① 欠損・遅延（最頻）**: 各ソースの最終更新時刻が想定更新間隔×1.5を超過（例：日次のはずが36時間更新なし）。
- **② 急変（ゼロ/スパイク）**: 前日比で指標が閾値外（0倍 or 3倍超）**かつ連動指標が動いていない**。impは正常でCVだけゼロ＝タグ外れ。**単独指標でなく連動指標の不整合で判定**（L1-2要因分解 imp×CTR×CVR を品質判定に転用）。
- **③ 整合性違反**: 論理矛盾（CV>click、cost>0かつimp=0、CTR>100%等）。
- **④ 定義ズレ（静かで危険）**: 分布シフト。明確な原因なく水準が持続的にシフト（ベースラインの段差）。L1-1トレンド検知を流用して段差検出。

### 人流データの品質チェック（穴#1・LM社データ版）

広告データの4ルールに加え、人流固有の品質異常を検知：
- **測位欠損**: LM社データの配信遅延・特定エリアの測位数急減（サンプル数が平常時の一定割合を下回る）。
- **エリア定義変更**: 道路リンク/メッシュIDの変更で時系列が断絶（突合の座標系正規化に影響）。
- **天候交絡との分離**: 人流急変が天候由来か実態かを、L1-1人流版の天候ベースライン補正で切り分けてから品質判定（誤って「データ異常」としない）。

人流が🔴の時は、ジオリフト・O2O分析を保留し「人流データ取得中」とUI明示。

### 信頼度ステータスと下流の振る舞い

| ステータス | 下流への影響 |
|---|---|
| 🟢 正常 | 通常通り全分析実行 |
| 🟡 注意 | 分析実行＋UIに「データ反映遅れ」注記 |
| 🔴 異常 | **該当指標のL1-1異常検知を抑制**、アクション生成保留、UI明示 |

🔴時の異常検知抑制が最重要。データ事故を実態の異常と誤り「CVゼロだから配信停止」等の誤アクションを防ぐ。これが品質レイヤーがL0の下にある理由。

### 決定事項

1. 4種検知：①欠損・遅延 ②急変（連動指標の不整合で判定）③整合性違反 ④定義ズレ（分布シフト/段差）。
2. 急変は単独でなく連動指標の不整合で見る（L1-2を品質判定に転用）。
3. 信頼度🟢🟡🔴。🔴時は該当指標のL1-1異常検知を抑制しアクション保留。
4. ベースラインはL1-1異常検知と共有（二重に持たない）。
5. 欠損は自動補正せず明示（精度の正直な開示）。

## 実装詳細5: 業種×レイヤー適用マトリクス（出し分けのSSOT）

「人流不要な業種では人流を出さない」を機械的に制御する仕組み。本マトリクスを出し分けの単一の真実（SSOT）とする。

### 業種フラグ

> **帰属単位（論点D）**: 業種フラグは「クライアント」でなく「**事業ライン（ワークスペース）**」に帰属する。1クライアントが複数事業ラインを持てる。例：アパレル企業が EC事業（useFootTraffic=false）と店舗事業（useFootTraffic=true）を別ラインとして持つ。本マトリクスの「業種」行は厳密には「事業ライン業種」を指す。

```
{
  industry_id,
  useFootTraffic: bool,    // 人流（横断軸A・A-2）
  usePromoCPP: bool,        // 販促CP（横断軸D）
  useO2OReconcile: bool,    // O2O突合（useFootTraffic && usePromoCPP が前提）
  useCRM_LTV: bool,         // CRM/LTV（突合③・実装詳細2）
  cv_definition: [...],     // L0成果定義（業種で異なる）
  b_industry_factor: float  // 指数bの業種係数（実装詳細4）
}
```

### 適用マトリクス

| 業種DB | オンラインL0-L3 | 人流(A/A-2) | 販促CP(D) | O2O突合 | CRM/LTV |
|---|---|---|---|---|---|
| EC/D2C | 必須 | OFF | 任意 | OFF | 任意 |
| B2B SaaS | 必須 | OFF | OFF | OFF | OFF |
| 薬局・小売 | 必須 | 必須 | 必須 | 必須 | 任意 |
| ポップアップ | 必須 | 必須 | 任意 | 任意 | OFF |
| 葬儀 | 必須 | OFF | OFF | OFF | OFF |
| ウェディング | 必須 | 任意 | 任意 | 任意 | 任意 |
| 不動産 | 必須 | 任意 | OFF | 任意 | 任意 |
| 飲食・店舗 | 必須 | 必須 | 任意 | 任意 | 任意 |

「必須」=常時ON、「任意」=オンボーディングで選択、「OFF」=実装・表示しない。

### 部分欠損への対応（フラグ＋判断Cバッジの役割分担）

フラグ=レイヤーのON/OFF、バッジ=データ充足度の濃淡。

| 状態 | 挙動 |
|---|---|
| 人流ON＋CP ON＋POS有 | 完全な二重接続、iROAS校正済み |
| 人流ON＋CP ON＋POS無 | 突合①のkを業種デフォルト、iROAS推定バッジ |
| 人流ON＋CP OFF | ジオリフト単独、増分来店まで（売上換算は推定） |
| 人流OFF | O2O層を丸ごと非表示、オンラインL0-L3のみ |

### 決定事項

1. 業種フラグで全出し分けを制御。依存（useO2OReconcile = useFootTraffic && usePromoCPP）はフラグ構造で表現。
2. 適用マトリクスを出し分けのSSOTとして設置。実装はこの表をコンフィグ化。
3. 各レイヤー冒頭に機械可読なガード条件を明記（false業種は実装・表示・アクション生成しない）。
4. フラグ（レイヤーON/OFF）と判断Cバッジ（データ充足度）で役割分担、部分欠損に対応。
5. マトリクスはデフォルト、オンボーディングで上書き可能。

### 事業ライン階層（複数業種クライアント・論点D）

1. 業種フラグは事業ライン（ワークスペース）に帰属。1クライアントが複数事業ラインを持てる。
2. 事業ラインごとに独立した業種フラグ・適用マトリクス・分析（実物の業種別ビューの拡張）。
3. 事業ライン分析＋全社ロールアップの2階層。ロールアップは論点C統合目的関数の円換算で統合成果を合算。
4. 予算配分は初期は事業ライン内で閉じる。ライン間配分は全社ビューの比較情報に留め、自動最適化は将来。
5. マトリクスの「業種」は「事業ライン業種」を指す。

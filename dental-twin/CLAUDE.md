# CLAUDE.md — DENTAL TWIN 開発の常設ルール

このファイルは Claude Code セッション全体で有効な規約。`SPEC.md` が仕様の単一情報源であり、
変更が入ったら **必ず `SPEC.md` を先に更新してからコードを書く**。

## 0. まず把握すること

```
SPEC.md      仕様（唯一の正）
README.md    引き継ぎ・現在地・アーキテクチャの要点
build.sh     生成→検証→ビルド→検証 のランナー。変更したら必ずこれを回す
src/         ビューア本体（viewer_app.js / viewer_shell.html）
tools/       ジェネレータと検証スクリプト
lib/         Three.js r128 固定。バージョンを上げない
dist/        生成物。手で編集しない（build.sh が上書きする）
```

**`dist/dental_twin_v1.html` を直接編集しないこと。** ビルド生成物であり、
次の `build.sh` で消える。編集対象は必ず `src/` 配下。

## 1. 絶対に守ること

1. **歯番は FDI (ISO 3950) の 2桁 integer が内部正。** Palmer / Universal は表示層でのみ変換する。
   変換テーブルはハードコードせず `NOTATION_MAP` として 1箇所に集約。
2. **歯面所見は「1歯面 = 1レコード」で保持する。** `"MOD"` のような文字列を主キーの一部にしない。
   表示用の連結文字列は導出値としてのみ扱う。
3. **自動診断ロジックを書かない。** う蝕の有無・重症度は必ず術者入力。
   画像やメッシュ形状から自動判定する処理は、明示的な指示があるまで実装しない（薬事上の理由）。
4. **患者データを HTML / JS に埋め込まない。** サンプルは必ず架空のダミーデータで、
   `patient_ref` は `P-000123` のような明らかな仮値にする。
5. **外部ネットワークへのリクエストを一切書かない。** CDN、フォント、API すべて禁止。
   ライブラリはインライン化する。院内クローズドネットワークで動くことが要件。
6. UI に「本表示は説明用であり診断結果を代替しません」の免責表記を常設する。削除しない。

## 2. 座標系（間違えるとすべて壊れる）

- 単位 **mm**、右手系、**Y-up**
- `+X` = 患者の左 / `+Y` = 頭頂 / `+Z` = 顔面前方
- 原点 = 正中矢状面 × 咬合平面 × 上顎中切歯唇面接線

外部データ（IOS の STL、購入モデル）は **必ず Z-up かつ原点バラバラ** だと想定して、
取り込み時に正規化パスを通す。**「たぶん合っている」で進めない。**
軸を触ったら必ず正面ビューのスクリーンショットで目視確認する。

## 3. Three.js r128 の既知の罠

- CDN 版 `OrbitControls` は使えない。**自前 orbit を実装する。**
- `THREE.ColorManagement.enabled = false` を先頭で明示（r152+ の既定と混ざらないように）。
- `AdditiveBlending` は明背景で白飛びする。ハイライトは `emissive` + `emissiveIntensity` で。
- `LineDashedMaterial` は視認性が低い。細い線は `TubeGeometry` か板ポリで。
- カメラ lerp 係数 0.12/frame は SwiftShader 下で収束が遅い。検証時は 12–16s 待つ。
- Draco デコード直後のメッシュは頂点が重複している。
  **法線再計算・トポロジ操作の前に必ず weld（マージ）する。**

## 3.5 メッシュ生成の罠（実装で踏んだもの）

1. **部分的な巻き順ミスは、全体の符号付き体積では検出できない。**
   歯冠側面が正しくても咬合面キャップだけ裏返っているケースが実際に起きた
   （体積は正のまま、Three.js の FrontSide で咬合面だけ透けて見える）。
   **部位ごとに `n·axis_occlusal` を検証する**こと。`verify_glb.py` に実装済み。
2. **ロフトの巻き順は「リングの進行方向」で決まる。**
   +Y に進むロフトは flip なしで外向き。-Y に進むロフト（歯根）は要 flip。
   内側へ収束するロフト（咬合面キャップ）は flip **なし**が外向き。直感と逆なので必ず数値で確認する。
3. **左右の歯は鏡像なので基底の行列式が反転する。** det(M)<0 の側は面の巻き順を反転する。
4. **咬合面観は対合顎を非表示にしないと成立しない。** カメラを真下/真上に置くと
   手前の顎が視界を完全に塞ぐ。プリセット側で `maxilla.visible` / `mandible.visible` を切り替える。
5. **歯肉は歯根長（最大17mm）を覆いきる深さが必要。** 浅いと根尖が歯肉から突き出す。
6. **口蓋・口腔底がないと咬合面観で弓の内側が素通しになる。** 見た目が破綻するので必須。

## 3.6 外部データ取り込み・幾何処理の罠（Phase 2 で踏んだもの）

1. **「正解姿勢のままのテストデータ」では回転の符号バグが検出できない。**
   面内 PCA の角度符号が逆でも θ=0 なら誤差ゼロになる。
   **必ず崩した姿勢（Z-up・別単位・傾き・原点ズレ）から復元させて検証する。**
2. **出力を同じ関数で再フィットする検査は循環している。**
   「正規化後の点群に平面を当てたら ±Y だった」は常に合格する。
   **既知の正解軸と直接比較する**こと。
3. **鏡像（左右反転）は寸法・幅の一致では検出できない。**
   歯番を追跡して `tooth_26` が +X 側かを見る。実際に一度混入した。
   左右取り違えは診療上の実害なので、検証に必ず入れる。
4. **IOS スキャンは「開いた面」。閉じたメッシュで検証しない。**
   境界（切り口）が歯肉側にあることが向き判定の最良の手掛かりで、
   閉じたメッシュではこれを試験できない。テストデータを実物に寄せる。
5. **開いた殻の PCA 最小軸 ≠ 咬合平面**（歯肉側の曲面に引かれて数度傾く）。
   臨床定義どおり**咬頭頂・切縁を通る平面**で取り直す。
6. **上下顎・咬合面の向きは自動判定に頼り切らない。** `--arch` で術者が指定するのを
   既定とし、推定したときは必ずフラグと警告を出す。確度も残す。
7. **正規化結果を自動的に「正しい」と扱わない。** `review_state: PENDING_REVIEW` を
   必ず持たせ、術者がプレビューで承認するまで Twin へ反映しない。
8. **歯番の並べ替えに x 座標を使わない。** 歯列弓は後方で内側へ湾曲するため、
   7番より8番の方が正中に近い x を取ることがある。**弓に沿った角度（弧長）で並べる。**
9. **実 IOS スキャンに歯根は写らない。** 歯根つきの合成データで検証すると、
   実データでは起こらない条件を試験してしまう。歯肉に隠れる部分は落とす。
10. **セグメンテーション・歯番付与は「解剖学的同定」で、診断ではない**ので実装してよい。
    ただし結果は必ず `SUGGESTED` とし、術者の Accept / Edit / Reject を経ること
    （欠損・埋伏があると歯番は必ずずれる）。
    **う蝕の自動検出は別（§1-3 で禁止）。混同しない。**

## 4. コード規約

- 成果物は **単一 HTML ファイル**。ビルドステップなし、外部依存なし。
- マジックナンバーは `CONFIG` オブジェクトに集約する。特に:
  - `CONFIG.SURFACE_PICK`（歯面判定の閾値: 咬合面の角度閾値、h_ratio 境界）
  - `CONFIG.COLORS`（配色。`SPEC.md` §9 と一致させる）
  - `CONFIG.CAMERA`（プリセット、lerp 係数）
- 機能追加は**非破壊拡張パターン**で行う。既知のアンカーコメントの直前に IIFE を追加し、
  既存関数は再代入でラップする。ラップ順序を変えない。
- 既存ファイルへの文字列パッチは Python で行い、必ず `assert h.count(old) == 1` で
  一意性を保証してから置換する。

## 5. 検証ルーチン（毎回・省略不可）

```
1) 最初の <script> と最後の </script> の間を抽出 → /tmp/check.js → node --check
   （HTML に直接 node --check をかけても動かない）
2) ローカル HTTP サーバを起動して Playwright で開く
   フラグ: --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader
   ※ バックグラウンドの HTTP サーバはツールコール間で死ぬ。毎回起動し直す。
3) 12–16s 待機してスクリーンショット（JPEG q68–80 / 長辺 ≤640px）
4) numpy/PIL でピクセル検証（配色が期待どおりの位置に出ているか）
5) 歯面判定の単体テスト: 32歯 × 各面の代表点でレイキャスト → 期待面と一致（合格 100%）
6) /mnt/user-data/outputs/ へ納品
```

## 6.5 UI ルール（一般歯科・分かりやすさ最優先）

これは好みではなく**要件**。逸脱しない。

1. **左右の明示を消さない。** 画面左右端の「患者さんの右 / 患者さんの左」は常時表示。
   3D の左右取り違えは診療上の実害につながる。
2. **グローブ着用前提。** タップ対象は最小 60×60px。**ホバー依存の機能と右クリックを実装しない**
   （コンテキストメニューは長押しに一本化）。
3. **メニューのネストを作らない。** タブの中のタブ、折りたたみの中の折りたたみは禁止。
4. **初期表示は「う蝕」レイヤのみ ON。** 全レイヤ同時 ON の初期状態にしない。
5. **凡例は常時表示。** 畳めるようにしない。
6. **モード切替で視点と選択歯を維持する。** 術者 ⇄ 患者モードで見ていた場所が変わるのは最悪。
7. **文字サイズ** 患者向け ≥18px / 術者向け ≥14px。`font-weight: 300` 以下を使わない。
8. **Undo を常設。** 破壊的操作には確認ダイアログ。
9. 起動から患者に見せるまで **3タップ以内**。新機能を追加するときこの条件を壊していないか確認する。

# DENTAL TWIN

歯科医院のチェアサイドで、**術者が入力した所見（う蝕・欠損・修復物・歯周状態）を
3D 口腔モデル上に可視化し、患者へ説明する**ためのツール。

株式会社YELLOW / 2026-08-16 / Phase 1 (B-3) 完了時点

---

## クイックスタート

```bash
./build.sh            # 生成 → 構造検証 → パイプライン検証 → ビルド → ビューア検証
./build.sh model      # モデル生成 + GLB 構造検証まで
./build.sh pipeline   # IOS 正規化 + DB 往復の検証のみ（Phase 2）
./build.sh viewer     # 単一HTMLビルド + Playwright 検証のみ

open dist/dental_twin_v1.html    # 成果物（単一HTML・外部通信ゼロ）

# IOS スキャンの取り込み（Phase 2）
python3 tools/ios_import.py scan.stl --arch upper
#   → dist/scan_normalized.stl + dist/scan_report.json (review_state=PENDING_REVIEW)

# DB との受け渡し（ファイル経由。ビューアは通信しない）
python3 tools/db_bridge.py export data/findings_sample.json -o dist/exam.sql
python3 tools/db_bridge.py import dist/rows.json -o dist/findings.json
```

## アーキテクチャの要点

### 1. GLB の `extras` がジオメトリとビューアの契約

ビューアはジオメトリの中身に一切依存しない。各 `tooth_<FDI>` ノードの `extras` だけを見る。

```json
{
  "fdi": 16, "type": "U6", "jaw": "U", "quadrant": 1, "roots": 3,
  "axis_occlusal": [...], "axis_buccal": [...], "axis_mesial": [...],
  "centroid": [...], "cej_h": 3.05, "crown_top_h": 10.55, "apex_h": -9.95,
  "bone_level_mm": 2.0
}
```

**購入モデルが届いたら、この `extras` を埋めた GLB を `dist/dental_template.glb` に
置き換えるだけでビューアは動く。** `tools/dental_arch_gen.py` は不要になる。

### 2. 歯面着色は頂点カラー（メッシュ分割しない）

読み込み時に全頂点を SPEC §5.1 の判定式で 5 面へソフト分類し、重み `W[n*5]` を保持する。
所見が変わったら「重み × 面色」の線形結合を計算し直すだけ。

- メッシュを面ごとに分割する必要がない → アセット作成コストが 1/5
- IOS 実データを取り込んでも同じロジックがそのまま動く
- 面の境界がグラデーションでつながる

### 3. 患者データは HTML に埋め込まない

`data/findings_sample.json` は**架空症例**。実患者データは
`<input type=file>` でローカル読み込みするか、将来 API から取得する。
ビルド時に実データを混ぜないこと。

### 4. PDF は「ページ全体を1枚の画像にして自前ライタで包む」（B-4）

外部依存ゼロの要件があるため jsPDF は使えない。かつ PDF 標準14フォントに日本語がなく、
CJK フォント埋め込みは単一HTMLのサイズを壊す。そこで **A4 全体を canvas
（1240×1754px = 150dpi）に描いて JPEG 化し、DCTDecode 画像1枚として1ページに配置**する。
`tools/verify_viewer.py` が xref のバイトオフセットと JPEG の SOI/EOI まで検証している。

### 5. 「現在の状態」と「シミュレーション」を分離する（B-3）

編集の唯一の対象は `S.baseDoc`（現在の所見）。治療後表示は
`simulateAfter(baseDoc)` が**毎回導出する使い捨ての値**で、保存もされない。
実測値（歯周6点法）はシミュレーションでも書き換えない。
ヘッダの KPI は常に baseDoc から計算する（SIMULATED ≠ ACTUAL を混ぜない）。

## 検証ルーチン（毎回・省略不可）

`./build.sh` が以下を自動で回す。

1. `node --check src/viewer_app.js`（HTML に直接かけても動かないので JS 単体で）
2. GLB 構造検証 — 歯番32本 / 軸の正規直交性 / `apex_h < cej_h < crown_top_h` /
   左右対称性 / 象限の X 符号 / 面法線の外向き / **咬合面の法線向き**
3. Playwright（SwiftShader フラグ）でビューア起動 → 16s 待機 → 操作 → スクリーンショット
4. 歯面判定テスト 32歯 × (B/L/M/D/O) = 160 点、**合格ライン 100%**

## 既知の落とし穴

`CLAUDE.md` に全て記載。特に重要な3点 + Phase 2 で踏んだもの:

**Phase 2（IOS 取り込み）で実際に踏んだ罠**

1. **「正解姿勢で 0 になる検査」は符号バグを素通しする。**
   面内 PCA の回転角の符号が逆でも、テストデータが最初から正しい姿勢だと
   θ=0 で誤差が出ない。**必ず崩した姿勢から復元させて検証する。**
2. **正規化した点群を同じ関数で再フィットする検査は循環していて無意味。**
   「咬合平面法線が ±Y か」は常に合格してしまう。**正解の軸と直接比べる。**
3. **左右反転（鏡像）は幅・寸法の一致では検出できない。**
   歯番（tooth_26 が +X 側か等）を追跡して初めて分かる。実際に一度混入した。
4. **閉じたメッシュで検証すると、実データ（開いた殻）で効く判定を試験できない。**
   IOS は開いた面で、境界＝歯肉側という強い手掛かりがある。テストデータの方を
   実物に寄せる（可視面だけ残す）ことで、正しい判定法を検証できるようにした。
5. **開いた殻の PCA 最小軸は咬合平面から数度ずれる**（歯肉側の曲面に引かれる）。
   臨床定義どおり咬頭頂を通る平面で取り直すと 3.84° → 0.86° に改善した。

1. **部分的な巻き順ミスは、メッシュ全体の符号付き体積では検出できない。**
   歯冠側面が正しくても咬合面キャップだけ裏返る事例が実際に起きた
   （症状：咬合面観で噛む面だけ透けて口蓋が見える）。部位別の法線検証が必須。
2. **左右の歯は鏡像なので基底の行列式が反転する。**
   `axis_mesial` を外積で導出してはいけない。3軸とも明示格納する。
   `det(M) < 0` の側は面の巻き順を反転する。
3. **Three.js r128 は CDN 版 OrbitControls が使えない。** 自前 orbit を実装済み。
   `lib/` のバージョンを上げないこと（r152+ で ColorManagement の既定が変わり配色が崩れる）。

## 法規上の位置づけ（設計制約）

- 本ツールは **「術者が確定した所見を可視化・説明するための表示ツール」**。診断は行わない。
- **自動でう蝕を検出・重症度を判定する機能を入れない。**
  入れた瞬間にプログラム医療機器（SaMD）該当性の議論が発生する。
- UI の免責表記を削除しない。
- 上市前に薬事の専門家の確認を取ること（SPEC §2）。
